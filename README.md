# Ethereum Builder

**Build and fix code on Ethereum and its Layer 2s — Base, Unichain, and Robinhood Chain.**

Live hub: https://kshot3000.github.io/Ethereum-Builder/

I'm Kyle Cox (@kshot9000), an independent builder. This repo is my home base for Ethereum work: an hourly loop builds and fixes code here, hunts verified bugs upstream across the Ethereum ecosystem, and ships tested, honest tools to the hub site. Progress digests land in [issue #1](https://github.com/Kshot3000/Ethereum-Builder/issues/1) (find it in the repo's Issues tab).

## Tools on the hub (browser-local, exact math, offline)

1. **Wei converter** — ETH ⇄ gwei ⇄ wei with BigInt decimal-string parsing. No floats.
2. **EIP-55 address inspector** — pure-JS Keccak-256 verifies and produces checksummed addresses; passes the official EIP-55 test vectors (covered in `tests/test-site.js`).
3. **EIP-1559 gas cost estimator** — gas × (base + priority) expected cost, and max cost at maxFeePerGas = 2×base + priority. Clearly a wallet-convention model, not live data.
4. **Function selector & event topic calculator** — Keccak-256 of a canonical signature gives the 4-byte calldata selector and the 32-byte event topic0; verified in the tests against the canonical ERC-20 selectors (`transfer(address,uint256)` → `0xa9059cbb`) and the Transfer/Approval topic hashes.
5. **CREATE2 address calculator** — EIP-1014 deterministic deployment addresses from deployer + salt + init code; verified in the tests against all seven official EIP-1014 examples. Computes the address only — nothing is deployed.
6. **ENS namehash calculator** — EIP-137 namehash (and the trailing label's labelhash) for a name, folded right-to-left with Keccak-256; verified in the tests against the official EIP-137 vectors (`''`, `eth`, `foo.eth`). ASCII labels only: internationalised names need full UTS-46 normalisation, so they are rejected rather than mis-hashed. Computes the identifier only — no name or resolver is looked up.

7. **EIP-712 domain separator calculator** — the `DOMAIN_SEPARATOR` for the canonical four-field `EIP712Domain` (name, version, chain ID, verifying contract), ABI-word encoded and hashed with Keccak-256; verified in the tests against the EIP-712 specification's own Ether Mail example (type hash `0x8b73c3c6…` and separator `0xf2cee375…`). Domains that omit fields or add a salt are out of scope rather than guessed at. Computes the separator only — nothing is signed.
8. **CREATE address calculator** — the classic deployment address, `keccak256(rlp([sender, nonce]))[12:]`, with a from-spec RLP encoder; verified in the tests against the long-published worked example for this formula (sender `0x6ac7…dbf0`, nonces 0–3) and the RLP specification's own encoding examples. Computes the address only — nothing is deployed.
9. **EIP-712 typed-data digest calculator (Ether Mail)** — the full signable digest `keccak256(0x1901 ‖ domainSeparator ‖ hashStruct(message))` for the EIP-712 specification's own example schema (`Mail` of two `Person` structs plus contents), with recursive struct hashing; verified in the tests against the published values in the EIP's example implementation (Mail type hash `0xa0cede…`, `hashStruct` `0xc52c0e…`, final digest `0xbe609a…`). That one fixed schema only — not a general typed-data encoder. Computes hashes only — nothing is signed.
10. **Proxy & namespaced storage slot calculator** — the ERC-1967 proxy slots (implementation, beacon, admin, plus rollback from the ERC's reference implementation) as `bytes32(uint256(keccak256(label)) − 1)`, and ERC-7201 namespaced-storage roots as `keccak256(abi.encode(uint256(keccak256(id)) − 1)) & ~0xff`; verified in the tests against the slot values published in ERC-1967 and ERC-7201's worked example for `example.main`. Computes slot constants only — no chain state is read.
11. **ABI calldata encoder** — encodes a full function call (selector + head/tail argument encoding) for `uint<M>`/`int<M>`, `address`, `bool`, `bytes<M>`/`bytes`, `string`, and fixed/dynamic arrays of those, nested, with integers carried as strings so no `uint256` ever loses precision; verified in the tests byte-for-byte against all five worked examples in the Solidity ABI specification (`baz`, `bar`, `sam`, `f`, and the nested `g`). Tuple and fixed-point types are rejected rather than guessed at. Encodes data only — nothing is sent and no transaction is made.
12. **ABI calldata decoder** — the strict inverse of the encoder: given a signature and calldata, it verifies the selector matches and decodes the arguments back, rejecting non-canonical encodings rather than tolerating them (out-of-range integer words, a bool other than 0/1, non-zero address leading bytes or padding, offsets into the head or past the end, invalid UTF-8 strings, truncated data, trailing bytes). Verified in the tests by decoding all five Solidity ABI specification examples back to their published arguments and re-encoding them byte-for-byte. Decodes data only — nothing is sent and no chain is queried.
13. **Merkle root & proof calculator** — builds a sorted-pair Keccak-256 tree over one leaf per line (`0x` lines contribute their hex bytes, other lines their UTF-8 bytes), the commutative pair hashing OpenZeppelin's `MerkleProof` uses on-chain, with odd nodes promoted unchanged; returns the root plus any leaf's proof and folds the proof back to the root as a self-check. Verified in the tests against an independent pure-Python Keccak-256 implementation written from the Keccak specification for this tool (roots and proofs for 4- and 5-leaf trees, including the promoted-odd-leaf proof), plus a hand-composed 2-leaf root. The page carries OpenZeppelin's 64-byte-leaf second-preimage caution. Computes hashes only — nothing is sent and no chain is queried.
14. **Raw transaction decoder** — strictly decodes a raw transaction's RLP (legacy incl. EIP-155, EIP-2930 type 1, EIP-1559 type 2, EIP-4844 type 3, EIP-7702 type 4) into every field plus the signing hash and transaction hash, rejecting non-canonical encodings rather than tolerating them (0x81-prefixed small bytes, long form for short payloads, leading-zero lengths/integers, wrong field counts, bad v, trailing bytes; signature decoded but not verified, no sender recovered). Type 4 set code transactions decode their authorization list too, with the EIP's own validity rules enforced (a destination is required, the authorization list may not be empty, each authorization's nonce must be below 2^64 and its y-parity below 2^8). Type 3 blob transactions decode their max fee per blob gas and blob versioned hashes too, with the EIP's own validity rules enforced (a destination is required, the versioned-hash list may not be empty, and every hash must be exactly 32 bytes starting with the KZG version byte 0x01); only the execution-payload form is decoded — the pooled network wrapper carrying the blobs, KZG commitments and proofs is refused, and no KZG proof is checked. Verified in the tests against the signed transaction published in EIP-155 itself — all fields and its published signing hash `0xdaf5a779…` — plus type 1 / type 2 / type 3 / type 4 vectors produced by an independent pure-Python RLP + Keccak oracle written from the specifications. Decodes data only — nothing is sent and no chain is queried.
15. **Signature recovery (ecrecover) calculator** — given a 32-byte digest and a signature's v / r / s, recovers the signer's address with pure-JS secp256k1 point arithmetic, exactly as the EVM's `ecrecover` precompile does; v is accepted as 0/1, 27/28, or an EIP-155 value, and `s` must be in the lower half of the curve order (the canonical EIP-2 form — the malleable high-s twin is rejected). Verified in the tests against three independent anchors: the EIP-155 example (its published signing hash and r/s recover the address an independent pure-Python secp256k1 oracle derives from the private key the EIP itself prints), EIP-712's printed `eth_signTypedData` signature recovering its published signing account over the spec digest, and Python-oracle sign/recover vectors with fixed keys. Recovers an address from a signature only — nothing is signed, no key is used, and no chain is queried.
16. **Signed message verification (EIP-191 personal_sign)** — given a message and the 65-byte signature a wallet returned, rebuilds the EIP-191 version-0x45 digest (`keccak256("\x19Ethereum Signed Message:\n" ‖ byte length ‖ message)` — the length counts UTF-8 bytes, not characters) and recovers the signer, with an optional expected-address comparison; exactly-65-byte signatures and the canonical low-`s` form are enforced, so malformed or malleable signatures are refused rather than half-verified. Verified in the tests against an independent pure-Python Keccak-256 + secp256k1 oracle written from the specifications (Keccak anchored on the published `''` / `hello world` vectors; address derivation anchored on the published addresses of private key 1 and of the private key EIP-155 prints), over an ASCII message, the empty message, and a multibyte UTF-8 message. Verifies a signature only — nothing is signed, no key is used, and no chain is queried.
17. **Transaction sender recovery** — composes the raw transaction decoder and the ecrecover calculator: strictly decode a signed transaction, recompute its signing hash from the unsigned payload, and recover the sender from the transaction's own v / r / s (legacy 27/28 or EIP-155 values, typed y-parity 0/1). Unsigned transactions are refused (they have no sender), and the canonical low-`s` form is enforced, so the malleable high-`s` twin of a signature is refused rather than recovered. For an EIP-7702 set code transaction it also recovers each authorization's authority from the tuple's own digest (`keccak256(0x05 ‖ rlp([chain_id, address, nonce]))`), reporting a tuple whose signature does not recover — including a high-`s` twin — with a null authority rather than a guessed account, exactly as a client skips that tuple. Verified in the tests against EIP-155's published transaction recovering its published sender, plus type 1 (Unichain 130), type 2 (Base 8453), legacy, type 3 (Ethereum L1, two blob versioned hashes), and type 4 (Base 8453, two authorizations signed by the two known keys) transactions signed by an independent pure-Python Keccak-256 + secp256k1 oracle written from the specifications with two known keys (private key 1 and the private key EIP-155 prints), each recovering that key's published address. Recovers addresses only — nothing is signed, no key is used, and no chain is queried.
18. **EIP-712 typed-data signature verification (Ether Mail)** — completes the digest calculator: given the same domain and `Mail` fields plus the 65-byte signature a wallet returned from `eth_signTypedData`, it recomputes the signable digest and recovers the signer, with an optional expected-signer comparison; exactly-65-byte signatures and the canonical low-`s` form are enforced, so malformed or malleable signatures are refused rather than half-verified. Verified in the tests against two independent anchors: the signature EIP-712 itself prints as the result of its example request, recovering its published signing account (Cow) over the published Ether Mail digest, and a signature over that digest produced by an independent pure-Python secp256k1 oracle (RFC 6979; address derivation anchored on the published addresses of private key 1 and of the private key EIP-155 prints) with private key 1. That one fixed schema only — not a general typed-data verifier. Verifies a signature only — nothing is signed, no key is used, and no chain is queried.

19. **RLP encoder & decoder** — exposes the codec the hub's other tools build on, in both directions. The encoder takes one value in a documented syntax (a `"quoted string"` or bare word as its UTF-8 bytes, a `0x` hex value as raw bytes, a decimal integer as the minimal big-endian byte string, or a nested `[list, of, values]`); the decoder is the strict canonical decoder the transaction tool uses (a `0x81`-prefixed small byte, the long length form for a short payload, leading-zero lengths, truncation, and trailing bytes are all refused) and a decoded value must re-encode to exactly the input bytes. Verified in the tests against the worked examples published in the ethereum.org RLP specification (the string `"dog"`, `["cat","dog"]`, the empty string and list, the integers 0 and 1024, the nested set-theoretic list, and the 56-byte Lorem ipsum string in its long length form) plus vectors from an independent pure-Python RLP encoder written from the same rules. Encodes and decodes data only — nothing is sent and no chain is queried.

21. **Next-block base fee calculator (EIP-1559)** — applies EIP-1559's own base-fee update rule to a parent block you supply: the gas target is the parent gas limit ÷ 2 (elasticity multiplier); a parent at target leaves the fee unchanged, above target the fee rises by `parent fee × (used − target) ÷ target ÷ 8` with a 1-wei floor on the rise (so a full parent raises it exactly 12.5%), and below target it falls by the same quotient with no floor — all exact BigInt arithmetic in wei. Inputs a real block cannot have are refused (gas used above the limit, a gas limit too small to have a target, gas values at or above 2^64). Verified in the tests against an independent pure-Python transcription of the EIP's validation pseudocode, itself anchored on closed forms: a full parent raises the fee by exactly fee÷8 (min 1 wei), an empty parent lowers it by exactly fee÷8, and a parent at target leaves it unchanged. This is the protocol's formula applied to supplied values, labelled as such — not live network data; nothing is sent and no chain is queried.

22. **Blob versioned hash calculator (EIP-4844)** — derives the 32-byte versioned hash a blob transaction carries from the blob's 48-byte KZG commitment, exactly as the EIP defines it: `0x01 ‖ sha256(commitment)[1:]`, the KZG version byte replacing the first byte of the commitment's SHA-256 (a from-spec pure-JS SHA-256 — the one place in the transaction format that uses SHA-256 rather than Keccak-256). Verified in the tests against the published FIPS 180-4 SHA-256 example digests (the empty string, `abc`, the 56-byte two-block example, and a million `a`s) for the hash itself, plus versioned-hash vectors from an independent Python `hashlib` transcription of the EIP's one-line definition (all-zero commitment, the BLS point-at-infinity encoding, sequential, descending, and seeded commitments); anything that is not exactly 48 bytes of hex is refused. Derives the hash from a commitment only — it does not compute the commitment from blob data (KZG/BLS cryptography needing a trusted-setup library), verify a KZG proof, or check that the bytes are a valid curve point. Computes hashes only — nothing is sent and no chain is queried.

23. **Intrinsic gas calculator (minimum gas limit)** — derives the gas limit a transaction must carry before any execution: 21,000 base + calldata at 4 gas per zero byte / 16 per non-zero byte + an EIP-2930 access list at 2,400 per address / 1,900 per storage key + (for a creation transaction) 32,000 and EIP-3860's 2 gas per 32-byte initcode word, with initcode over 49,152 bytes refused + (for an EIP-7702 set-code transaction) 25,000 per authorization, refused in combination with creation — then takes the larger of that standard cost and EIP-7623's Prague calldata floor, 21,000 + 10 per calldata token (zero byte = 1 token, non-zero = 4). Verified in the tests against an independent pure-Python transcription of the four EIPs' rules, covering the empty transfer (21,000), the floor binding on data-heavy calldata, creation at and over the initcode limit, access-list and authorization totals. Labelled as a minimum, not a prediction of total gas used; L2s add their own fees. Computes locally — nothing is sent and no chain is queried.

24. **Uniswap V2 pair & V3 pool address calculator** — derives the CREATE2 address a Uniswap pair/pool lives at from the factory, the two tokens, and the published init code hash, exactly as Uniswap's developer docs (V2) and the v3-periphery `PoolAddress` library (V3) define it: tokens are sorted so the smaller address is token0 (identical or zero-address tokens are refused, as the factories refuse them), the V2 salt is Keccak-256 of the two token addresses packed (40 bytes), and the V3 salt is Keccak-256 of `abi.encode(token0, token1, fee)` with the fee a non-zero uint24. Factory and init code hash are editable inputs — the defaults are the canonical Ethereum-mainnet deployment — so Base, Unichain, and fork deployments work with their own values. Verified in the tests against the canonical mainnet addresses (V2 USDC/WETH, DAI/WETH, WBTC/WETH pairs and the V2 docs' worked example; V3 USDC/WETH at the 0.05% and 0.3% tiers, WETH/USDT and DAI/WETH at 0.3%), each reproduced first by an independent pure-Python Keccak-256 + CREATE2 oracle. Computes the address only — whether a pair/pool exists there is the factory's `getPair`/`getPool` chain query, which the hub does not make; nothing is deployed and no chain is queried.

25. **Uniswap V2 swap quote calculator** — prices a swap against a V2 pair with the exact integer math of `UniswapV2Library` (v2-periphery): for an exact input, the output with the 0.3% fee applied as a 997/1000 factor, rounded down; for an exact output, the required input solved the other way and rounded up by 1, as the library rounds, so the pair's invariant check passes; plus a spot quote that is just the reserve ratio (no fee, no price movement — not a trade quote). Reserves and amounts are in each token's base units; reserves at or above 2^112 are refused (the pair stores them as uint112), an exact output must be below the output reserve, and an exact input too small to buy 1 base unit is refused (the pair reverts on a zero-output swap). Price impact against the pre-trade reserve ratio, fee included, is shown truncated to 4 decimal places. Verified in the tests against an independent pure-Python transcription of the library's three formulas, including uint112-max reserves and a round-trip minimality property (the required input reproduces the quoted output, and 1 unit less does not). Reserves are user-supplied values — a real pair's reserves are chain state this page does not read — so this is the formula applied to supplied values, not live pool data; single pair only, and 0.3%-fee pairs only. Computes locally — nothing is swapped and no chain is queried.

27. **Uniswap V3 liquidity amounts calculator** — works out what a concentrated-liquidity position holds with the exact integer math of `LiquidityAmounts` (v3-periphery) over `SqrtPriceMath` (v3-core), all divisions floored: amounts mode returns the token amounts for a liquidity L between a lower and an upper tick at the current tick (all token0 at or below the range, all token1 at or above it, split inside it, rounded down as the library computes position amounts), and liquidity mode returns the L a desired amount pair mints (the single-sided formula outside the range, the minimum of the two sides inside it) plus the amounts that L actually uses. Ticks are converted with the hub's TickMath, so every price is one a real pool can hold; liquidity is a uint128 in the contracts, so an L at or above 2^128 is refused, as is a desired pair too small to mint L of 1. Verified in the tests against an independent pure-Python transcription of the two libraries' formulas (sqrt ratios taken from the already-verified TickMath), covering in-range, boundary, below-range and above-range positions, the full ±887272 range, a 2^127-scale liquidity, and exact round-trips. Ticks and amounts are user-supplied values — a real position's ticks and liquidity and the pool's current tick are chain state this page does not read — not live pool data. Computes locally — nothing is deposited and no chain is queried.

28. **Uniswap V3 swap step calculator** — prices one step of a V3 swap inside a single tick range with the exact integer math of `SwapMath.computeSwapStep` (v3-core) over `SqrtPriceMath`: the target tick's price bounds the step and sets its direction (below the current price swaps token0 for token1, above swaps token1 for token0), exact-input mode spends the specified amount, exact-output mode seeks it and is capped at what the range holds, input-side amounts round up and output-side amounts round down exactly as the library passes its rounding flags, and when an exact-input step stops short of the target the whole leftover input is the fee (the library's remainder rule), otherwise the fee is the rounded-up `amountIn × feePips / (1e6 − feePips)`. The remainder a following step would continue with is reported. Verified in the tests against an independent pure-Python transcription of the two libraries, covering both directions and modes, steps that reach the target and steps that stop short, the capped-output branch, a zero fee tier, a 1-unit input taken entirely as fee, the minimum tick as target, and 2^100 liquidity. Prices, liquidity and amounts are user-supplied values — a real pool's price, liquidity and fee tier are chain state this page does not read, and a full swap crosses initialized ticks with changing liquidity, which a single step does not model — not a live quote and not financial advice. Computes locally — nothing is swapped and no chain is queried.

26. **Uniswap V3 tick ⇄ sqrtPriceX96 converter** — converts between a V3 pool's tick and its sqrtPriceX96 (`sqrt(1.0001^tick) × 2^96`, the Q64.96 square root of the token1/token0 price) with the exact integer math of `TickMath` in v3-core, in both directions: forward as the library's Q128.128 factor product divided by 2^32 rounding up, and back as the greatest tick whose sqrt ratio is at most the input, via the library's log2 bracketing resolved against the forward direction. Ticks are bounded by ±887272; a sqrt ratio must satisfy MIN_SQRT_RATIO ≤ s < MAX_SQRT_RATIO, so the maximum tick's own ratio is refused in the reverse direction, exactly as the library requires. The raw price `(sqrtPriceX96 / 2^96)^2` is shown truncated to 12 significant digits and ignores token decimals (a human price also scales by 10^(decimals0 − decimals1)). Verified in the tests against an independent pure-Python transcription of TickMath, cross-checked against the published MIN/MAX_SQRT_RATIO anchors, an exact-integer isqrt evaluation of `sqrt(1.0001^tick) × 2^96`, and a 361-tick round-trip. Values are user-supplied — a real pool's tick and sqrtPriceX96 are its `slot0` chain state, which the hub does not read — not live pool data. Computes locally — nothing is swapped and no chain is queried.

20. **Blob gas & blob base fee calculator (EIP-4844 / EIP-7691)** — applies the blob market's own pricing rule to parent-block values you supply: the excess-blob-gas update (`calc_excess_blob_gas`) and the base fee per blob gas (`fake_exponential(1, excess, update_fraction)`, the Taylor approximation the EIP specifies, in exact BigInt arithmetic), then totals the burned blob fee for a transaction's blob count (131,072 blob gas each). Both parameter schedules are offered — Cancun as EIP-4844 launched it (target 3 blobs, max 6, fraction 3,338,477) and Prague as EIP-7691 raised it (target 6, max 9, fraction 5,007,716) — and a parent block that used more than the schedule's maximum is refused rather than extrapolated. Verified in the tests against an independent pure-Python transcription of the EIPs' pseudocode (whose `fake_exponential` at 10× the update fraction reproduces ⌊e¹⁰⌋ = 22,026 on both schedules), covering the excess edges (below target floors at 0, exactly target holds, full blocks add the above-target remainder, a high excess decays by the target) and busy-chain fees on both schedules. This is the protocol's pricing rule applied to supplied values, labelled as such — not live network data; nothing is sent and no chain is queried.

## Scope

- **Ethereum L1** — clients and tooling: reth, Lodestar, Prysm, viem, ethers.js, ERC standards.

# Ethereum Builder

**Build and fix code on Ethereum and its Layer 2s — Base, Unichain, and Robinhood Chain.**

Live hub: https://kshot3000.github.io/Ethereum-Builder/

I'm Kyle Cox (@kshot9000), an independent builder. ## Tools on the hub (browser-local, exact math, offline)

1. **Wei converter** — ETH ⇄ gwei ⇄ wei with BigInt decimal-string parsing. No floats.
2. **EIP-55 address inspector** — pure-JS Keccak-256 verifies and produces checksummed addresses; passes the official EIP-55 test vectors (covered in `tests/test-site.js`).
3. **EIP-1559 gas cost estimator** — gas × (base + priority) expected cost, and max cost at maxFeePerGas = 2×base + priority. Clearly a wallet-convention model, not live data.
4. **Function selector & event topic calculator** — Keccak-256 of a canonical signature gives the 4-byte calldata selector and the 32-byte event topic0; verified in the tests against the canonical ERC-20 selectors (`transfer(address,uint256)` → `0xa9059cbb`) and the Transfer/Approval topic hashes.
5. **CREATE2 address calculator** — EIP-1014 deterministic deployment addresses from deployer + salt + init code; verified in the tests against all seven official EIP-1014 examples. Computes the address only — nothing is deployed.
6. **ENS namehash calculator** — EIP-137 namehash (and the trailing label's labelhash) for a name, folded right-to-left with Keccak-256; verified in the tests against the official EIP-137 vectors (`''`, `eth`, `foo.eth`). ASCII labels only: internationalised names need full UTS-46 normalisation, so they are rejected rather than mis-hashed. Computes the identifier only — no name or resolver is looked up.

7. **EIP-712 domain separator calculator** — the `DOMAIN_SEPARATOR` for the canonical four-field `EIP712Domain` (name, version, chain ID, verifying contract), ABI-word encoded and hashed with Keccak-256; verified in the tests against the EIP-712 specification's own Ether Mail example (type hash `0x8b73c3c6…` and separator `0xf2cee375…`). Domains that omit fields or add a salt are out of scope rather than guessed at. Computes the separator only — nothing is signed.
8. **CREATE address calculator** — the classic deployment address, `keccak256(rlp([sender, nonce]))[12:]`, with a from-spec RLP encoder; verified in the tests against the long-published worked example for this formula (sender `0x6ac7…dbf0`, nonces 0–3) and the RLP specification's own encoding examples. Computes the address only — nothing is deployed.
9. **EIP-712 typed-data digest calculator (Ether Mail)** — the full signable digest `keccak256(0x1901 ‖ domainSeparator ‖ hashStruct(message))` for the EIP-712 specification's own example schema (`Mail` of two `Person` structs plus contents), with recursive struct hashing; verified in the tests against the published values in the EIP's example implementation (Mail type hash `0xa0cede…`, `hashStruct` `0xc52c0e…`, final digest `0xbe609a…`). That one fixed schema only — not a general typed-data encoder. Computes hashes only — nothing is signed.
10. **Proxy & namespaced storage slot calculator** — the ERC-1967 proxy slots (implementation, beacon, admin, plus rollback from the ERC's reference implementation) as `bytes32(uint256(keccak256(label)) − 1)`, and ERC-7201 namespaced-storage roots as `keccak256(abi.encode(uint256(keccak256(id)) − 1)) & ~0xff`; verified in the tests against the slot values published in ERC-1967 and ERC-7201's worked example for `example.main`. Computes slot constants only — no chain state is read.
11. **ABI calldata encoder** — encodes a full function call (selector + head/tail argument encoding) for `uint<M>`/`int<M>`, `address`, `bool`, `bytes<M>`/`bytes`, `string`, and fixed/dynamic arrays of those, nested, with integers carried as strings so no `uint256` ever loses precision; verified in the tests byte-for-byte against all five worked examples in the Solidity ABI specification (`baz`, `bar`, `sam`, `f`, and the nested `g`). Tuple and fixed-point types are rejected rather than guessed at. Encodes data only — nothing is sent and no transaction is made.
12. **ABI calldata decoder** — the strict inverse of the encoder: given a signature and calldata, it verifies the selector matches and decodes the arguments back, rejecting non-canonical encodings rather than tolerating them (out-of-range integer words, a bool other than 0/1, non-zero address leading bytes or padding, offsets into the head or past the end, invalid UTF-8 strings, truncated data, trailing bytes). Verified in the tests by decoding all five Solidity ABI specification examples back to their published arguments and re-encoding them byte-for-byte. Decodes data only — nothing is sent and no chain is queried.
13. **Merkle root & proof calculator** — builds a sorted-pair Keccak-256 tree over one leaf per line (`0x` lines contribute their hex bytes, other lines their UTF-8 bytes), the commutative pair hashing OpenZeppelin's `MerkleProof` uses on-chain, with odd nodes promoted unchanged; returns the root plus any leaf's proof and folds the proof back to the root as a self-check. Verified in the tests against an independent pure-Python Keccak-256 implementation written from the Keccak specification for this tool (roots and proofs for 4- and 5-leaf trees, including the promoted-odd-leaf proof), plus a hand-composed 2-leaf root. The page carries OpenZeppelin's 64-byte-leaf second-preimage caution. Computes hashes only — nothing is sent and no chain is queried.
14. **Raw transaction decoder** — strictly decodes a raw transaction's RLP (legacy incl. EIP-155, EIP-2930 type 1, EIP-1559 type 2, EIP-4844 type 3, EIP-7702 type 4) into every field plus the signing hash and transaction hash, rejecting non-canonical encodings rather than tolerating them (0x81-prefixed small bytes, long form for short payloads, leading-zero lengths/integers, wrong field counts, bad v, trailing bytes; signature decoded but not verified, no sender recovered). Verified in the tests against the signed transaction published in EIP-155 itself — all fields and its published signing hash `0xdaf5a779…` — plus type 1 / type 2 / type 3 / type 4 vectors produced by an independent pure-Python RLP + Keccak oracle written from the specifications. Decodes data only — nothing is sent and no chain is queried.
15. **Signature recovery (ecrecover) calculator** — given a 32-byte digest and a signature's v / r / s, recovers the signer's address with pure-JS secp256k1 point arithmetic, exactly as the EVM's `ecrecover` precompile does; v is accepted as 0/1, 27/28, or an EIP-155 value, and `s` must be in the lower half of the curve order (the canonical EIP-2 form — the malleable high-s twin is rejected). Verified in the tests against three independent anchors: the EIP-155 example (its published signing hash and r/s recover the address an independent pure-Python secp256k1 oracle derives from the private key the EIP itself prints), EIP-712's printed `eth_signTypedData` signature recovering its published signing account over the spec digest, and Python-oracle sign/recover vectors with fixed keys. Recovers an address from a signature only — nothing is signed, no key is used, and no chain is queried.
16. **Signed message verification (EIP-191 personal_sign)** — given a message and the 65-byte signature a wallet returned, rebuilds the EIP-191 version-0x45 digest (`keccak256("\x19Ethereum Signed Message:\n" ‖ byte length ‖ message)` — the length counts UTF-8 bytes, not characters) and recovers the signer, with an optional expected-address comparison; exactly-65-byte signatures and the canonical low-`s` form are enforced, so malformed or malleable signatures are refused rather than half-verified. Verifies a signature only — nothing is signed, no key is used, and no chain is queried.
17. **Transaction sender recovery** — composes the raw transaction decoder and the ecrecover calculator: strictly decode a signed transaction, recompute its signing hash from the unsigned payload, and recover the sender from the transaction's own v / r / s (legacy 27/28 or EIP-155 values, typed y-parity 0/1). Verified in the tests against EIP-155's published transaction recovering its published sender, plus type 1 (Unichain 130), type 2 (Base 8453), legacy, type 3 (Ethereum L1, two blob versioned hashes), and type 4 (Base 8453, two authorizations signed by the two known keys) transactions signed by an independent pure-Python Keccak-256 + secp256k1 oracle written from the specifications with two known keys (private key 1 and the private key EIP-155 prints), each recovering that key's published address. Recovers addresses only — nothing is signed, no key is used, and no chain is queried.

19. **RLP encoder & decoder** — exposes the codec the hub's other tools build on, in both directions. The encoder takes one value in a documented syntax (a `"quoted string"` or bare word as its UTF-8 bytes, a `0x` hex value as raw bytes, a decimal integer as the minimal big-endian byte string, or a nested `[list, of, values]`); the decoder is the strict canonical decoder the transaction tool uses (a `0x81`-prefixed small byte, the long length form for a short payload, leading-zero lengths, truncation, and trailing bytes are all refused) and a decoded value must re-encode to exactly the input bytes. Verified in the tests against the worked examples published in the ethereum.org RLP specification (the string `"dog"`, `["cat","dog"]`, the empty string and list, the integers 0 and 1024, the nested set-theoretic list, and the 56-byte Lorem ipsum string in its long length form) plus vectors from an independent pure-Python RLP encoder written from the same rules. Encodes and decodes data only — nothing is sent and no chain is queried.

21. **Next-block base fee calculator (EIP-1559)** — applies EIP-1559's own base-fee update rule to a parent block you supply: the gas target is the parent gas limit ÷ 2 (elasticity multiplier); a parent at target leaves the fee unchanged, above target the fee rises by `parent fee × (used − target) ÷ target ÷ 8` with a 1-wei floor on the rise (so a full parent raises it exactly 12.5%), and below target it falls by the same quotient with no floor — all exact BigInt arithmetic in wei. Inputs a real block cannot have are refused (gas used above the limit, a gas limit too small to have a target, gas values at or above 2^64). Verified in the tests against an independent pure-Python transcription of the EIP's validation pseudocode, itself anchored on closed forms: a full parent raises the fee by exactly fee÷8 (min 1 wei), an empty parent lowers it by exactly fee÷8, and a parent at target leaves it unchanged. This is the protocol's formula applied to supplied values, labelled as such — not live network data; nothing is sent and no chain is queried.

22. **Blob versioned hash calculator (EIP-4844)** — derives the 32-byte versioned hash a blob transaction carries from the blob's 48-byte KZG commitment, exactly as the EIP defines it: `0x01 ‖ sha256(commitment)[1:]`, the KZG version byte replacing the first byte of the commitment's SHA-256 (a from-spec pure-JS SHA-256 — the one place in the transaction format that uses SHA-256 rather than Keccak-256). Verified in the tests against the published FIPS 180-4 SHA-256 example digests (the empty string, `abc`, the 56-byte two-block example, and a million `a`s) for the hash itself, plus versioned-hash vectors from an independent Python `hashlib` transcription of the EIP's one-line definition (all-zero commitment, the BLS point-at-infinity encoding, sequential, descending, and seeded commitments); anything that is not exactly 48 bytes of hex is refused. Derives the hash from a commitment only — it does not compute the commitment from blob data (KZG/BLS cryptography needing a trusted-setup library), verify a KZG proof, or check that the bytes are a valid curve point. Computes hashes only — nothing is sent and no chain is queried.

23. **Intrinsic gas calculator (minimum gas limit)** — derives the gas limit a transaction must carry before any execution: 21,000 base + calldata at 4 gas per zero byte / 16 per non-zero byte + an EIP-2930 access list at 2,400 per address / 1,900 per storage key + (for a creation transaction) 32,000 and EIP-3860's 2 gas per 32-byte initcode word, with initcode over 49,152 bytes refused + (for an EIP-7702 set-code transaction) 25,000 per authorization, refused in combination with creation — then takes the larger of that standard cost and EIP-7623's Prague calldata floor, 21,000 + 10 per calldata token (zero byte = 1 token, non-zero = 4). Verified in the tests against an independent pure-Python transcription of the four EIPs' rules, covering the empty transfer (21,000), the floor binding on data-heavy calldata, creation at and over the initcode limit, access-list and authorization totals. Labelled as a minimum, not a prediction of total gas used; L2s add their own fees. Computes locally — nothing is sent and no chain is queried.

36. **Compound account liquidity calculator (getHypotheticalAccountLiquidity)** — decides whether an account may borrow or redeem, and whether it is liquidatable at all, with the Comptroller's own Exp-step math (compound-protocol, BSD-3-Clause; formulas paraphrased) applied to one market: `tokensToDenom = (collateralFactor × exchangeRate ÷ 10^18) × oraclePrice ÷ 10^18` in two truncating steps — so the factor can differ from the one-line product whenever an intermediate product is not a multiple of 10^18 and the price is large enough to amplify the discarded remainder — `collateral = tokensToDenom × cTokenBalance ÷ 10^18`, against `borrows + effects = oraclePrice × borrowBalance ÷ 10^18 + tokensToDenom × hypotheticalRedeem ÷ 10^18 + oraclePrice × hypotheticalBorrow ÷ 10^18`, each term truncating once; collateral above the borrow side is liquidity, anything else (equality included) leaves the difference as shortfall. Computes locally — nothing is borrowed, redeemed or liquidated and no chain is queried.

38. **Compound borrow allowed calculator (borrowAllowed)** — runs the Comptroller's borrow gate (compound-protocol, BSD-3-Clause; formulas paraphrased) in its own branch order: a zero oracle price returns the price error first (the cap addition and liquidity products are never computed, so an overflow in either is not a refusal there); then the market borrow cap — 0 means unlimited (the addition is never computed then either), otherwise `nextTotalBorrows = totalBorrows + borrowAmount` with checked addition (an overflow is refused) and the contract requires nextTotalBorrows strictly below the cap, so landing exactly on the cap is refused as cap-reached, before the liquidity check; then the liquidity calculator's hypothetical check with the proposed borrow applied, where a shortfall above zero blocks the borrow and a shortfall of exactly zero (the borrow exhausting liquidity exactly) is allowed. 41. **Compound exit market calculator (exitMarket)** — runs the Comptroller's exit flow (compound-protocol, BSD-3-Clause; formulas paraphrased) in its own branch order: the account's snapshot is read first and any amount owed in the market refuses the exit at once as a nonzero borrow balance — before every membership step, so a non-member owing a balance is refused there too, and price and factor are never read on that path; only an account owing nothing reaches the internal redeem check run with the redeem amount set to the account's full cToken balance, where a non-member bypasses the liquidity check entirely and a member runs the liquidity calculator's hypothetical check — whose borrow balance is the (zero) amount owed and whose redeem term is computed from exactly the same inputs as its collateral term, so the two cancel identically and the check completes at liquidity 0 and shortfall 0, its only remaining refusals being a zero oracle price and any product or sum above the uint256 maximum. 42. **ModExp precompile gas calculator (EIP-2565 / EIP-7883)** — prices a call to the EVM's modular-exponentiation precompile (address `0x05`) under both schedules that have priced it, transcribed from the two EIPs' published pseudocode (both CC0): multiplication complexity from `words = ceil(max(base length, modulus length) ÷ 8)` — `words²` under EIP-2565; a flat 16 at a maximum of at most 32 bytes and `2 × words²` above it under EIP-7883 — times an iteration count from the exponent (0 for a zero exponent of at most 32 bytes, otherwise its bit length − 1 for a short exponent, and for a longer one 8 (EIP-2565) or 16 (EIP-7883) per byte past 32 plus the bit length − 1 of the exponent's head, its first 32 bytes; the count is floored at 1), charged as `max(200, complexity × iteration ÷ 3)` under EIP-2565 and `max(500, complexity × iteration)` under EIP-7883. Verified in the tests against an independent pure-Python transcription of the two pseudocodes, itself anchored on the EIPs' own test tables: a 64-byte base and modulus with exponent `0x10001` reproduces the `modexp_nagydani_1_pow0x10001` row under both schedules (341 / 2,048 gas) and a 1,024-byte pair the `nagydani_5` row (87,381 / 524,288). Both schedules are shown because which applies is the chain's fork state (Ethereum mainnet applies EIP-7883 since Fusaka); the EIP-7823 input-length caps are a validity rule, not part of the pricing, and are not modelled. Lengths and the exponent head are user-supplied values — no chain is queried; computes locally — nothing is called and no exponentiation is performed.

43. **SSTORE gas & refund calculator (EIP-2200 / EIP-2929 / EIP-3529)** — prices one `SSTORE` under net gas metering (EIP-2200, CC0; formulas paraphrased) with the parameters current mainnet applies: warm read cost 100 and a 2,100 cold surcharge on a slot's first touch in a transaction (EIP-2929, CC0), reset cost 2,900, clearing schedule 4,800 (EIP-3529, CC0). 44. **Memory expansion gas calculator** — prices growing a call frame's memory under the Yellow Paper's memory-cost function (as implemented by go-ethereum's `memoryGasCost` with its `MemoryGas` = 3 and `QuadCoeffDiv` = 512 parameters; formulas paraphrased): holding `w` 32-byte words costs in total `3w + floor(w² ÷ 512)`, and an expansion is charged only the difference between the new and current totals — nothing when memory does not grow — so stepwise expansions telescope to the one-shot cost. The quadratic term is zero below 23 words, reaches the linear term's scale at 512 words (16 KiB, total 2,048), and dominates beyond it. Byte sizes round up to whole words on both sides; a size above 137,438,953,440 bytes (0x1FFFFFFFE0) is refused, as the client's gas calculation overflows there. The prefilled growth (empty to 1,024 bytes) is 32 words and exactly 98 gas. Verified in the tests against an independent pure-Python transcription of the cost function, itself anchored in-script on hand values (1 word = 3, 32 words = 98, 512 words = 2,048, quadratic onset at 23 words), the no-growth rule, word rounding, and a telescoping assert over stepwise expansions. Computes locally — nothing is executed and no chain is queried.
45. **CALL gas calculator (EIP-2929 / EIP-150)** — prices one `CALL` and the split of the caller's gas, under the rules current mainnet applies (EIP-2929, EIP-150, EIP-161; all CC0, formulas paraphrased, cross-checked against go-ethereum's `gasCall` / `callGas`): the call's own cost is charged first — account access 2,600 for a cold target address or 100 for a warm one, 9,000 if the call carries value, 25,000 more if it carries value and the target account is empty (nonce 0, balance 0, no code), plus memory expansion for the input and output regions together (the frame must reach the larger region end; a zero-size region touches nothing whatever its offset) — and if the available gas is below that base the CALL runs out of gas and forwards nothing. Of the remainder R, at most `R − floor(R ÷ 64)` can be forwarded (the all-but-one-64th rule, as the client computes it), the callee receives min(requested, that cap) plus a 2,300 stipend when value is carried — added for the callee, not deducted from the caller — and the caller keeps the rest at the moment of the call (gas the callee leaves unused returns afterwards). The prefilled call (cold, 1 ETH to an existing account, 100,000 available, 1,000,000 requested) pays an 11,600 base, forwards 87,019, delivers 89,319 with the stipend, and keeps exactly its 1,381 reserve. Verified in the tests against an independent pure-Python transcription of the rules, itself anchored in-script on hand values (the prefilled split, remainder 63 forwarding whole and 64 forwarding 63, the empty-target surcharge applying only with value) and a conservation assert (base + forwarded + retained = available, the stipend extra) over every non-out-of-gas vector. Honest scope: only `CALL` is modelled — CALLCODE, DELEGATECALL and STATICCALL share the access and forwarding rules but differ on the value terms; a call the caller cannot fund fails for a non-gas reason that is not modelled; and warmth, target state, value and memory are user-supplied values, not execution state this page reads. Computes locally — nothing is called and no chain is queried.

Computes locally — nothing is deployed and no chain is queried.

# Ethereum Builder

**Build and fix code on Ethereum and its Layer 2s — Base, Unichain, and Robinhood Chain.**

3. **EIP-1559 gas cost estimator** — gas × (base + priority) expected cost, and max cost at maxFeePerGas = 2×base + priority. Clearly a wallet-convention model, not live data.
4. **Function selector & event topic calculator** — Keccak-256 of a canonical signature gives the 4-byte calldata selector and the 32-byte event topic0; verified in the tests against the canonical ERC-20 selectors (`transfer(address,uint256)` → `0xa9059cbb`) and the Transfer/Approval topic hashes.
5. **CREATE2 address calculator** — EIP-1014 deterministic deployment addresses from deployer + salt + init code; verified in the tests against all seven official EIP-1014 examples. Computes the address only — nothing is deployed.
6. **ENS namehash calculator** — EIP-137 namehash (and the trailing label's labelhash) for a name, folded right-to-left with Keccak-256; verified in the tests against the official EIP-137 vectors (`''`, `eth`, `foo.eth`). ASCII labels only: internationalised names need full UTS-46 normalisation, so they are rejected rather than mis-hashed. Computes the identifier only — no name or resolver is looked up.

7. **EIP-712 domain separator calculator** — the `DOMAIN_SEPARATOR` for the canonical four-field `EIP712Domain` (name, version, chain ID, verifying contract), ABI-word encoded and hashed with Keccak-256; verified in the tests against the EIP-712 specification's own Ether Mail example (type hash `0x8b73c3c6…` and separator `0xf2cee375…`). Domains that omit fields or add a salt are out of scope rather than guessed at. Computes the separator only — nothing is signed.
8. **CREATE address calculator** — the classic deployment address, `keccak256(rlp([sender, nonce]))[12:]`, with a from-spec RLP encoder; verified in the tests against the long-published worked example for this formula (sender `0x6ac7…dbf0`, nonces 0–3) and the RLP specification's own encoding examples. Computes the address only — nothing is deployed.
9. **EIP-712 typed-data digest calculator (Ether Mail)** — the full signable digest `keccak256(0x1901 ‖ domainSeparator ‖ hashStruct(message))` for the EIP-712 specification's own example schema (`Mail` of two `Person` structs plus contents), with recursive struct hashing; verified in the tests against the published values in the EIP's example implementation (Mail type hash `0xa0cede…`, `hashStruct` `0xc52c0e…`, final digest `0xbe609a…`). That one fixed schema only — not a general typed-data encoder. Computes hashes only — nothing is signed.
10. **Proxy & namespaced storage slot calculator** — the ERC-1967 proxy slots (implementation, beacon, admin, plus rollback from the ERC's reference implementation) as `bytes32(uint256(keccak256(label)) − 1)`, and ERC-7201 namespaced-storage roots as `keccak256(abi.encode(uint256(keccak256(id)) − 1)) & ~0xff`; verified in the tests against the slot values published in ERC-1967 and ERC-7201's worked example for `example.main`. Computes slot constants only — no chain state is read.
11. **ABI calldata encoder** — encodes a full function call (selector + head/tail argument encoding) for `uint<M>`/`int<M>`, `address`, `bool`, `bytes<M>`/`bytes`, `string`, and fixed/dynamic arrays of those, nested, with integers carried as strings so no `uint256` ever loses precision; verified in the tests byte-for-byte against all five worked examples in the Solidity ABI specification (`baz`, `bar`, `sam`, `f`, and the nested `g`). Tuple and fixed-point types are rejected rather than guessed at. Encodes data only — nothing is sent and no transaction is made.
12. **ABI calldata decoder** — the strict inverse of the encoder: given a signature and calldata, it verifies the selector matches and decodes the arguments back, rejecting non-canonical encodings rather than tolerating them (out-of-range integer words, a bool other than 0/1, non-zero address leading bytes or padding, offsets into the head or past the end, invalid UTF-8 strings, truncated data, trailing bytes). Verified in the tests by decoding all five Solidity ABI specification examples back to their published arguments and re-encoding them byte-for-byte. Decodes data only — nothing is sent and no chain is queried.
13. **Merkle root & proof calculator** — builds a sorted-pair Keccak-256 tree over one leaf per line (`0x` lines contribute their hex bytes, other lines their UTF-8 bytes), the commutative pair hashing OpenZeppelin's `MerkleProof` uses on-chain, with odd nodes promoted unchanged; returns the root plus any leaf's proof and folds the proof back to the root as a self-check. Verified in the tests against an independent pure-Python Keccak-256 implementation written from the Keccak specification for this tool (roots and proofs for 4- and 5-leaf trees, including the promoted-odd-leaf proof), plus a hand-composed 2-leaf root. The page carries OpenZeppelin's 64-byte-leaf second-preimage caution. Computes hashes only — nothing is sent and no chain is queried.
14. **Raw transaction decoder** — strictly decodes a raw transaction's RLP (legacy incl. EIP-155, EIP-2930 type 1, EIP-1559 type 2, EIP-4844 type 3, EIP-7702 type 4) into every field plus the signing hash and transaction hash, rejecting non-canonical encodings rather than tolerating them (0x81-prefixed small bytes, long form for short payloads, leading-zero lengths/integers, wrong field counts, bad v, trailing bytes; signature decoded but not verified, no sender recovered). Verified in the tests against the signed transaction published in EIP-155 itself — all fields and its published signing hash `0xdaf5a779…` — plus type 1 / type 2 / type 3 / type 4 vectors produced by an independent pure-Python RLP + Keccak oracle written from the specifications. Decodes data only — nothing is sent and no chain is queried.
15. **Signature recovery (ecrecover) calculator** — given a 32-byte digest and a signature's v / r / s, recovers the signer's address with pure-JS secp256k1 point arithmetic, exactly as the EVM's `ecrecover` precompile does; v is accepted as 0/1, 27/28, or an EIP-155 value, and `s` must be in the lower half of the curve order (the canonical EIP-2 form — the malleable high-s twin is rejected). Recovers an address from a signature only — nothing is signed, no key is used, and no chain is queried.

Verifies a signature only — nothing is signed, no key is used, and no chain is queried.
17. **Transaction sender recovery** — composes the raw transaction decoder and the ecrecover calculator: strictly decode a signed transaction, recompute its signing hash from the unsigned payload, and recover the sender from the transaction's own v / r / s (legacy 27/28 or EIP-155 values, typed y-parity 0/1). Recovers addresses only — nothing is signed, no key is used, and no chain is queried.

19. **RLP encoder & decoder** — exposes the codec the hub's other tools build on, in both directions. 21. **Next-block base fee calculator (EIP-1559)** — applies EIP-1559's own base-fee update rule to a parent block you supply: the gas target is the parent gas limit ÷ 2 (elasticity multiplier); a parent at target leaves the fee unchanged, above target the fee rises by `parent fee × (used − target) ÷ target ÷ 8` with a 1-wei floor on the rise (so a full parent raises it exactly 12.5%), and below target it falls by the same quotient with no floor — all exact BigInt arithmetic in wei. Inputs a real block cannot have are refused (gas used above the limit, a gas limit too small to have a target, gas values at or above 2^64). Verified in the tests against an independent pure-Python transcription of the EIP's validation pseudocode, itself anchored on closed forms: a full parent raises the fee by exactly fee÷8 (min 1 wei), an empty parent lowers it by exactly fee÷8, and a parent at target leaves it unchanged. This is the protocol's formula applied to supplied values, labelled as such — not live network data; nothing is sent and no chain is queried.

22. **Blob versioned hash calculator (EIP-4844)** — derives the 32-byte versioned hash a blob transaction carries from the blob's 48-byte KZG commitment, exactly as the EIP defines it: `0x01 ‖ sha256(commitment)[1:]`, the KZG version byte replacing the first byte of the commitment's SHA-256 (a from-spec pure-JS SHA-256 — the one place in the transaction format that uses SHA-256 rather than Keccak-256). Verified in the tests against the published FIPS 180-4 SHA-256 example digests (the empty string, `abc`, the 56-byte two-block example, and a million `a`s) for the hash itself, plus versioned-hash vectors from an independent Python `hashlib` transcription of the EIP's one-line definition (all-zero commitment, the BLS point-at-infinity encoding, sequential, descending, and seeded commitments); anything that is not exactly 48 bytes of hex is refused. Derives the hash from a commitment only — it does not compute the commitment from blob data (KZG/BLS cryptography needing a trusted-setup library), verify a KZG proof, or check that the bytes are a valid curve point. Computes hashes only — nothing is sent and no chain is queried.

23. **Intrinsic gas calculator (minimum gas limit)** — derives the gas limit a transaction must carry before any execution: 21,000 base + calldata at 4 gas per zero byte / 16 per non-zero byte + an EIP-2930 access list at 2,400 per address / 1,900 per storage key + (for a creation transaction) 32,000 and EIP-3860's 2 gas per 32-byte initcode word, with initcode over 49,152 bytes refused + (for an EIP-7702 set-code transaction) 25,000 per authorization, refused in combination with creation — then takes the larger of that standard cost and EIP-7623's Prague calldata floor, 21,000 + 10 per calldata token (zero byte = 1 token, non-zero = 4). Verified in the tests against an independent pure-Python transcription of the four EIPs' rules, covering the empty transfer (21,000), the floor binding on data-heavy calldata, creation at and over the initcode limit, access-list and authorization totals. Verified in the tests against an independent pure-Python transcription of the semantics, itself anchored in-script on hand values (1 << 255 exact, SHL of the maximum wrapping to 2^256 − 2, the shift-256 saturation trio, SAR of -255 at -128 against SDIV's -127, the prefilled -256 >> 4 at -16), covering all three opcodes, the 255/256 shift boundary and hex/decimal equivalence. Honest scope: the shift and value are user-supplied values, in decimal or 0x hex, not execution state this page reads; an input wider than 2^256 − 1 is refused rather than wrapped, because the stack words cannot hold it (the SHL result still wraps, as the opcode's does). Computes locally — nothing is executed and no chain is queried.

67. **Modular arithmetic opcode calculator — ADDMOD / MULMOD** — computes what the EVM's two modular-arithmetic opcodes push for operands a, b and a modulus N you supply, together with their flat 8-gas charge (Frontier opcodes; the semantics are restated here in my own words and were cross-verified this run across several independent opcode references). ADDMOD (0x08) pushes (a + b) mod N and MULMOD (0x09) pushes (a × b) mod N, with the intermediate sum or product computed at FULL precision — never reduced mod 2^256 first, so an ADDMOD sum can reach 2^257 − 2 and a MULMOD product 2^512 − 2^257 + 1. That precision is the pair's entire purpose (Solidity's `addmod` / `mulmod` built-ins compile to exactly these opcodes, for arithmetic over large prime fields) and its trap: (2^255 × 2) mod (2^255 − 19) is 38 at full precision, but a calculator that wraps the product to a word first answers 0. A modulus of 0 pushes 0 for both opcodes, the raw opcode rule matching MOD/DIV by zero — Solidity's built-ins instead check first and revert with Panic(0x12), a language-level check this calculator deliberately does not imitate, since it computes the opcode. The operands are read unsigned, a and b are interchangeable, and N is the third, deepest popped word. The prefilled call (MULMOD, a = 2^255, b = 2, N = 2^255 − 19, the Curve25519 field prime) pushes exactly 38. Verified in the tests against an independent pure-Python transcription of the semantics, itself anchored in-script on hand values (15 % 6 = 3, 56 % 6 = 2, 45 % 8 = 5, the zero-modulus and modulus-1 cases, (−1)² mod (2^255 − 19) = 1, and the prefilled 38 against the wrapping answer 0), covering operands above the modulus, the maximal words against the maximal modulus, a product of exactly 2^256, and hex/decimal equivalence. Honest scope: a, b and N are user-supplied values, in decimal or 0x hex, not execution state this page reads; an input wider than 2^256 − 1 is refused rather than wrapped, because the stack words cannot hold it (the intermediate, by contrast, is never wrapped — that asymmetry is the feature). Computes locally — nothing is executed and no chain is queried.

68. **BYTE opcode calculator** — computes what the EVM's BYTE opcode (0x1a) pushes for an index i and a word x you supply, together with its flat 3-gas charge (a Frontier opcode; the semantics are restated here in my own words and were cross-verified this run against evm.codes and a client implementation). BYTE pops the index first, then the word, and pushes the byte of x at position i — counting byte 0 as the MOST significant byte, so the byte extracted is (x >> (248 − 8×i)) & 0xff — placed at the least significant position of the pushed word, so the result is always 0–255. That end convention is the trap: SIGNEXTEND counts its byte index from the least significant end, BYTE from the most significant end, so the same index selects opposite bytes in the two opcodes, and a least-significant-first implementation passes every symmetric test while being wrong at both ends. An index of 32 or more pushes 0 — out of range is a defined result, not an error. The prefilled call (index 0 of 0xab00000000000000000000000000000000000000000000000000000000000001) pushes exactly 171 (0xab), where a least-significant-first reading would push 1; at index 31 the true answer is 1. Verified in the tests against an independent pure-Python transcription that extracts the byte through a big-endian byte array, itself anchored in-script on hand values (the prefilled 171 / 1 pair, the published evm.codes examples — 0xff at index 31 of 0xff and at index 30 of 0xff00 — and the sequential word 0x000102…1f whose byte k is k), covering the 31/32 index boundary, the maximal index and word, and hex/decimal equivalence. Honest scope: the index and value are user-supplied values, in decimal or 0x hex, not execution state this page reads; an input wider than 2^256 − 1 is refused rather than wrapped, because the stack words cannot hold it. Computes locally — nothing is executed and no chain is queried.

69. **Division & modulo opcode calculator — DIV / SDIV / MOD / SMOD** — computes what the EVM's four division opcodes push for a dividend a and a divisor b you supply, together with their flat 5-gas charge (Frontier opcodes; the semantics are restated here in my own words and were cross-verified this run against independent opcode references). DIV (0x04) and MOD (0x06) read the operands unsigned; SDIV (0x05) and SMOD (0x07) read them as two's-complement signed; the dividend is popped first. A divisor of 0 pushes 0 for all four — division by zero is a defined result at the opcode level, not an error (Solidity's `/` and `%` check first and revert with Panic(0x12); that check is the language's, not the opcode's). SDIV truncates toward zero — −255 ÷ 2 pushes −127, not the −128 a floor division gives, and −1 ÷ 2 pushes 0 — and it carries the EVM's one arithmetic overflow: −2^255 ÷ −1 pushes the −2^255 word itself, since the true quotient 2^255 fits no signed word. SMOD's result takes the sign of the dividend, never the divisor: −255 mod 2 pushes −1 and 255 mod −2 pushes 1, the opposite of a floor-mod in both mixed-sign cases. The prefilled call (SDIV, a = the word 0xffff…ff01 reading as −255, b = 2) pushes exactly −127, where a flooring implementation answers −128. Verified in the tests against an independent pure-Python transcription that handles signed values through absolute values and an explicit sign (because Python's `//` and `%` floor, the exact behaviour the opcodes do not have), itself anchored in-script on hand values (DIV/MOD by zero, the −127 truncation and −1 ÷ 2 = 0 cases, the −2^255 ÷ −1 overflow word, both SMOD sign cases), covering maximal words, the signed minimum against ±1 and 2, and hex/decimal equivalence. Honest scope: a and b are user-supplied values, in decimal or 0x hex, not execution state this page reads; an input wider than 2^256 − 1 is refused rather than wrapped, because the stack words cannot hold it. Computes locally — nothing is executed and no chain is queried.

70. **Comparison opcode calculator — LT / GT / SLT / SGT / EQ / ISZERO** — computes what the EVM's six comparison opcodes push for operands a and b you supply, together with their flat 3-gas charge (Frontier opcodes, the verylow tier; the semantics are restated here in my own words). The five binary opcodes pop a first, then b, and push 1 when the comparison holds and 0 when it does not — a comparison pushes 1 or 0, never an operand — and the comparisons are strict, so equal operands push 0 for LT, GT, SLT and SGT. ISZERO (0x15) is unary: it pops one word only and pushes 1 exactly when that word is 0 (the calculator never reads b for it). LT (0x10) and GT (0x11) read the operands unsigned; SLT (0x12) and SGT (0x13) read the same words as signed two's-complement integers, so one pair of words can answer oppositely under the two pairs: the all-ones word is the largest unsigned value but reads as −1 signed, so against 1 it makes LT push 0 and SLT push 1, GT push 1 and SGT push 0 — an implementation that compares every word unsigned passes every small-number test and is wrong on exactly the words with the top bit set. EQ (0x14) alone is reading-independent. The prefilled call (SLT, a = the all-ones word reading as −1, b = 1) pushes exactly 1, where LT on the same words pushes 0. Verified in the tests against an independent pure-Python transcription that derives the signed readings by subtracting 2^256 from words at or above 2^255 and then compares as plain integers, itself anchored in-script on hand values (the all-ones flip in both pairs, strictness at equality, the signed minimum against 0 in both readings, EQ at equality, ISZERO at 0 and at the maximum word), covering maximal words, the signed minimum, and hex/decimal equivalence. Honest scope: a and b are user-supplied values, in decimal or 0x hex, not execution state this page reads; an input wider than 2^256 − 1 is refused rather than wrapped, because the stack words cannot hold it. Computes locally — nothing is executed and no chain is queried.

71. **Bitwise opcode calculator — AND / OR / XOR / NOT** — computes what the EVM's four bitwise opcodes push for operands a and b you supply, together with their flat 3-gas charge (Frontier opcodes, the verylow tier; the semantics are restated here in my own words). The three binary opcodes pop a first, then b, and push the bit-by-bit combination of the two words — a result bit is 1 exactly when both input bits are 1 (AND, 0x16), when at least one is 1 (OR, 0x17), or when exactly one is 1 (XOR, 0x18). They operate on the raw 256 bits, so there is no signed pair and the words' signed or unsigned reading is irrelevant, and the three are commutative (a and b interchangeable, unlike SUB, DIV or LT). NOT (0x19) is unary: it pops one word only and pushes that word with every one of its 256 bits flipped, so NOT 0 pushes the all-ones word and NOT of the all-ones word pushes 0. The trap: NOT is not negation — there is no NEG opcode, arithmetic negation is 0 − x (a SUB), and the two's-complement identity is −x = NOT(x) + 1, so NOT 1 pushes 0xffff…fffe (reading as −2 signed), not the all-ones word (reading as −1); an implementation that computes NOT as 0 − x, or borrows a language whose ~ is infinite-precision (Python's ~0 is −1), is off by one on every input. The prefilled call (NOT of 0) pushes exactly 2^256 − 1. Verified in the tests against an independent pure-Python transcription using Python's bitwise operators with NOT computed as MAX ^ a rather than Python's ~, itself anchored in-script on hand values (12 & 10 = 8, 12 | 10 = 14, 12 ^ 10 = 6, NOT 0 = the all-ones word, NOT 1 = MAX − 1 against the MAX that 0 − 1 gives, the complementary 0xaa…/0x55… patterns), covering maximal words, complementary patterns, and hex/decimal equivalence. Honest scope: a and b are user-supplied values, in decimal or 0x hex, not execution state this page reads; an input wider than 2^256 − 1 is refused rather than wrapped, because the stack words cannot hold it. Computes locally — nothing is executed and no chain is queried.

72. **Arithmetic opcode calculator — ADD / MUL / SUB** — computes what the EVM's three plain arithmetic opcodes push for operands a and b you supply, together with their gas charges (Frontier opcodes; the semantics are restated here in my own words). Each pops a first, then b, and pushes the result reduced modulo 2^256: ADD (0x01) pushes (a + b) mod 2^256, MUL (0x02) pushes (a × b) mod 2^256, and SUB (0x03) pushes (a − b) mod 2^256 with a as the minuend. The defining rule is the wrap: no result traps, saturates or signals, so the all-ones word plus 1 pushes 0, 0 − 1 pushes the all-ones word, 2^255 × 2 pushes 0 and 2^255 × 3 pushes 2^255; the checked overflow/underflow reverts of Solidity ≥ 0.8 are a language check around these opcodes, not the opcodes themselves. SUB is not commutative (3 − 5 pushes 2^256 − 2, not 2) while ADD and MUL are, and there is no signed pair in this family — modulo-2^256 addition, multiplication and subtraction give the same word under either reading. Gas is not uniform inside the family: ADD and SUB are a flat 3 (verylow tier) while MUL is a flat 5 (low tier). The prefilled call (SUB, a = 0, b = 1) pushes exactly 2^256 − 1. Verified in the tests against an independent pure-Python transcription that reduces Python's arbitrary-precision +, * and − modulo 2^256 explicitly, itself anchored in-script on hand values (2 + 3 = 5, 2 × 3 = 6, 5 − 3 = 2, MAX + 1 = 0, 0 − 1 = MAX, 2^255 × 2 = 0, 2^255 × 3 = 2^255, SUB's non-commutativity, the 3-vs-5 gas split), covering maximal words, wrap edges, and hex/decimal equivalence. Honest scope: a and b are user-supplied values, in decimal or 0x hex, not execution state this page reads; an input wider than 2^256 − 1 is refused rather than wrapped, because the stack words cannot hold it (the result still wraps, as the opcode's does). Computes locally — nothing is executed and no chain is queried.

73. **Push opcode calculator — PUSH0 / PUSH1–PUSH32** — computes what the EVM's push opcodes push for the immediate bytes you supply, together with their gas charges (PUSH1–PUSH32 Frontier, PUSH0 from EIP-3855 in Shanghai; the semantics are restated here in my own words). PUSHn (0x60–0x7f) reads the n bytes after the opcode byte as a big-endian integer — those bytes are the high-order bytes of the pushed word — while PUSH0 (0x5f) has no immediate and pushes 0. The trap is truncation at the end of the code: if fewer bytes remain than the opcode reads, the missing bytes are the low-order ones and read as zero (the byte string is padded on the right), so a truncated PUSH2 carrying only 0xff pushes 0xff00 = 65280, not 255; an implementation that pads on the left is wrong on exactly the pushes a disassembler meets at code end. Gas splits inside the family: PUSH0 is a flat 2 (base tier) while every PUSH1–PUSH32 is a flat 3 (verylow tier) whatever its width or value — the 1-gas saving over PUSH1 0x00, plus a saved code byte, is PUSH0's whole reason to exist. The calculator also names the smallest push of the same value (a PUSH5 of 0x0000000001 pushes 1, which PUSH1 pushes in fewer bytes; 0 belongs to PUSH0). The prefilled call (PUSH2, immediate 0xff) pushes exactly 65280 with 1 byte padded. Verified in the tests against an independent pure-Python transcription that pads the supplied bytes on the right with zeros to length n and reads them big-endian, itself anchored in-script on hand values (PUSH1 0xff = 255, PUSH2 0xff = 65280, PUSH2 0x0102 = 258, PUSH4 0xdeadbeef = 3735928559, a 20-byte address word, PUSH32 of the all-ones word, the 2-vs-3 gas split), covering truncation at several widths, empty immediates, and minimal-push derivations. Honest scope: the immediate bytes are user-supplied values, not code this page reads; supplying more bytes than the opcode reads is refused rather than silently cut, because the extra bytes would be the next instruction. Computes locally — nothing is executed and no chain is queried.
74. **Stack opcode calculator — POP / DUP1–DUP16 / SWAP1–SWAP16** — applies one of the EVM's stack-shuffling opcodes to a stack you supply (listed deepest first, top item last) and computes the resulting stack, together with the opcode's gas charge (all Frontier; the semantics are restated here in my own words). POP (0x50) removes the top item; DUPn (0x80–0x8f) pushes a copy of the n-th item counting the TOP as 1, so DUP1 copies the top itself and the copied item stays in place (depth grows by exactly 1); SWAPn (0x90–0x9f) exchanges the top item with the (n+1)-th, so SWAP1 swaps the top two and the depth never changes. Counting from the bottom instead — the deepest item as 1 — is the family's classic implementation bug: it passes on shallow stacks and duplicates or swaps exactly the wrong word whenever the stack runs deeper than the index. A too-short stack has no defined result at all (unlike DIV by zero or an out-of-range BYTE): DUPn on fewer than n items, SWAPn on fewer than n+1, or POP on an empty stack is a stack underflow, an exceptional halt that consumes the frame's remaining gas and reverts its state, and the calculator reports the halt with the stack unchanged rather than inventing a result. Gas is a flat 2 for all three families — the base tier, one below the verylow 3 the push family charges, so copying that 3 overprices every DUP and SWAP by half again. The prefilled call (DUP3 of 10, 20, 30 with 30 on top) pushes a second copy of exactly 10, the deepest item. Verified in the tests against an independent pure-Python transcription that keeps the stack as a list with the top last (DUPn appends element −n, SWAPn exchanges elements −1 and −(n+1)), itself anchored in-script on hand values (DUP1 of [10, 20, 30] is [10, 20, 30, 30] — the copy of the top; SWAP2 of [1, 2, 3] is [3, 2, 1]; DUP16 and SWAP16 at their exact depth boundaries; POP of an empty stack), covering the orientation cases, both underflow boundaries, maximal words, and the flat-2 charge. Honest scope: the stack items are user-supplied values, not execution state this page reads; at most 64 items are accepted (a real stack caps at 1024, and the mirror-image overflow of a DUP at that cap is out of scope here), and any word wider than 256 bits is refused rather than wrapped. Computes locally — nothing is executed and no chain is queried.

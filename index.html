Ethereum in 30 seconds

Ethereum L1 is the settlement layer: a global computer where smart contracts run and every transaction is secured by the full network. It is powerful but capacity-limited, so most everyday activity moves to Layer 2 rollups — chains that execute transactions cheaply off L1 and post proofs/data back to Ethereum, inheriting its security. Since EIP-1559, every L1 transaction burns a base fee that floats with demand, plus an optional priority fee (tip) — the estimator below models exactly that.

Base is Coinbase's L2, built on the OP Stack / Superchain. Unichain is Uniswap's L2, built for DeFi and cross-chain liquidity. Robinhood Chain is Robinhood's permissionless L2 for onchain finance and tokenized real-world assets, built on Arbitrum technology with ETH as its gas token — live per its official documentation. Same EVM, same Solidity, same tooling (viem, ethers.js, Foundry) across all of them — which is why one builder hub can cover all four.

CREATE2 address calculator (EIP-1014)

CREATE2 deploys a contract to an address you can know in advance: the last 20 bytes of Keccak-256 of 0xff ++ deployer ++ salt ++ keccak256(init code). Same deployer, salt and init code → same address on Ethereum, Base, Unichain and Robinhood Chain — the basis for counterfactual wallets and cross-chain deployments. Defaults below are EIP-1014's own Example 0. This only computes the address locally; nothing is deployed.

Uniswap V2 pair & V3 pool address calculator

Uniswap's factories deploy every pair and pool with CREATE2, so the address is fixed before the pair exists — by the factory, the two tokens, and the pair/pool bytecode's init code hash. This calculator runs that derivation locally, exactly as Uniswap's developer docs (V2) and the v3-periphery PoolAddress library (V3) publish it: the tokens are sorted so the numerically smaller address is token0 (the factories refuse identical or zero-address tokens, and so does this tool), the V2 salt is Keccak-256 of the two token addresses packed (40 bytes), while the V3 salt is Keccak-256 of abi.encode(token0, token1, fee) (three 32-byte words). The defaults are the canonical Ethereum-mainnet deployment, and the prefilled V3 example reproduces the well-known USDC/WETH 0.3% pool. Switching protocol swaps the factory and init code hash defaults to that protocol's — unless you have typed your own, which is never overwritten: on Base, Unichain, or a fork, enter that deployment's factory (and its init code hash, if it was compiled differently). A V3 fee must be a tier the factory has enabled, which is chain state. Honest scope: this computes where a pair/pool would live — whether one actually exists there is the factory's getPair/getPool chain query, which this page does not make. Computed locally; nothing is deployed and no chain is queried.

Uniswap V2 swap quote calculator

Found the pair with the calculator above — this prices a swap against it, with the exact integer math of UniswapV2Library in v2-periphery. A V2 pair holds the constant product of its two reserves and charges 0.3% on the input, applied as a 997/1000 factor: for an exact input the output is the fee-adjusted input times the output reserve, divided by the input reserve scaled by 1000 plus the fee-adjusted input, rounded down; for an exact output the required input is the same relation solved the other way, rounded up by 1 so the pair's invariant check passes. The third mode, spot quote, is just the reserve ratio — no fee, no price movement, and not a trade quote. Enter reserves and amounts in each token's base units (the raw integers the contracts use); the pair stores reserves as uint112, so a reserve at or above 2112 is refused. Price impact is measured against the pre-trade reserve ratio, includes the fee, and is shown truncated to 4 decimal places (the amounts themselves are exact). Single pair only — a multi-hop route chains this per hop — and forks charging a fee other than 0.3% are out of scope. Honest scope: the reserves are values you supply — a real pair's reserves are chain state (its getReserves), which this page does not read, so this is the library's formula applied to supplied values, not live pool data and not financial advice. Computed locally; nothing is swapped and no chain is queried.

Uniswap V2 liquidity mint & burn calculator

Priced a swap above — this works out the liquidity side of the same pair, with the exact integer math of UniswapV2Pair in v2-core (and its Math library's Babylonian integer square root). Mint: into an existing pair, the LP units minted are the minimum of the two sides' pro-rata amounts, amount × totalSupply ÷ reserve floored per side — so the scarcer side relative to the pair's ratio governs and an unbalanced deposit earns no credit for its excess. Into an empty pair (the first deposit, reserves and total supply all 0), the units minted are sqrt(amount0 × amount1) − 1000: the first 1000 units (MINIMUM_LIQUIDITY) are locked at the zero address forever. Burn: LP units pay out pro-rata from the pair's token balances — not its reserves, since balances can exceed reserves by donations and accrued fees — liquidity × balance ÷ totalSupply floored per side. A mint or burn that would pay out 0 on a side is refused, as the pair reverts, and no reserve or balance (or reserve plus deposit) may exceed 2112 − 1, the pair's uint112 storage bound. Amounts are in base units. The prefilled mint (10,000 / 40,000 into reserves of 1,000,000 / 4,000,000 with supply 2,000,000) mints exactly 20,000 LP units; the prefilled burn (10,000 LP units against balances of 1,010,000 / 4,040,000 and the resulting supply of 2,020,000) pays out exactly 5,000 / 20,000. Honest scope: reserves, balances and total supply are values you supply — a real pair's are chain state, which this page does not read — and the pair's optional protocol-fee mint (when the factory's feeTo is set) is not modelled, so the total supply you supply is taken as the supply at the liquidity event itself. This is the pair contract's formula applied to supplied values, not live pool data and not financial advice. Computed locally; nothing is deposited, burned or queried on chain.

ERC-4626 vault conversion calculator

A tokenized vault (ERC-4626) prices its shares against the assets it holds with a single exchange rate, applied the way OpenZeppelin's ERC4626 applies it — with virtual shares and one virtual asset added to the totals, the construction that blunts the first-deposit inflation attack: converting assets to shares multiplies by (totalSupply + 10offset) ÷ (totalAssets + 1), and shares to assets by the inverse, where the offset is the vault's _decimalsOffset() (0 in OpenZeppelin's default). The four modes are the standard's four preview functions, and each rounds in the vault's favour, exactly as the standard specifies: previewDeposit (assets in, shares out) and previewRedeem (shares in, assets out) round down, while previewMint (shares wanted, assets needed) and previewWithdraw (assets wanted, shares burned) round up. Enter totals and amounts in base units. The prefilled vault (1,000,000 assets backing 1,000,000 shares, offset 0) converts a deposit of 10,000 assets to exactly 10,000 shares — try the same deposit against a supply of 1 share and a million assets to see a deposit round to 0 shares, then raise the offset to 3 and watch it mint 1. Honest scope: totals are values you supply — a real vault's totalAssets and totalSupply are chain state, which this page does not read — and a vault's own limits (maxDeposit, balances, allowances) are not modelled. This is the standard's formula applied to supplied values, not live vault data and not financial advice. Computed locally; nothing is deposited and no chain is queried.

Compound cToken exchange rate & mint/redeem calculator

A Compound money market prices its cTokens with one exchange rate, computed the way CToken computes it: while no cTokens exist the stored rate is the market's initial exchange rate mantissa, and afterwards it is (cash + totalBorrows − totalReserves) × 1018 ÷ totalSupply, truncated — so the rate only grows as borrows accrue interest faster than reserves skim their share. Conversions run through the same rate with ExponentialNoError's truncating Exp math: minting mints amount × 1018 ÷ rate cTokens, redeeming cTokens pays tokens × rate ÷ 1018 underlying, and redeeming a chosen underlying amount burns amount × 1018 ÷ rate cTokens. Note the contrast with the ERC-4626 tool above: Compound truncates every step and never rounds up, so the prefilled market (8,000,000 cash, 3,000,000 borrows, 100,000 reserves, 500,000,000 cTokens supplied; rate 21800000000000000) mints 45,871,559 cTokens for 1,000,000 underlying, and redeeming exactly those cTokens pays back 999,999 — one base unit stays in the market. Amounts are in base units of each token (cTokens have 8 decimals, the underlying usually 18, which is why an initial rate like cDAI's 2×1026 looks large: it is the per-token rate scaled by 1018 across that decimal gap). Honest scope: totals are values you supply — a real market's cash, borrows, reserves and supply are chain state, which this page does not read — interest accrual up to the current block (exchangeRateCurrent) is not performed, and Comptroller liquidity checks, cash-availability checks and borrow/repay are not modelled. This is CToken's formula applied to supplied values, not live market data and not financial advice. Computed locally; nothing is supplied or redeemed and no chain is queried.

Compound interest accrual calculator (accrueInterest)

The exchange-rate tool above reads a Compound market's stored totals; this one performs the step that moves them. CToken's accrueInterest takes the market's per-block borrow rate (a mantissa scaled by 1018, as its interest rate model returns it) and the blocks elapsed since the last accrual, and computes a simple interest factor — rate × blocks — then, truncating at every step through ExponentialNoError: interest accumulated is factor × totalBorrows ÷ 1018, total borrows grow by that interest, total reserves grow by reserveFactor × interest ÷ 1018, and the borrow index grows to factor × borrowIndex ÷ 1018 + borrowIndex. Two behaviours worth seeing: it is simple interest over the gap (the rate is held constant for one accrual call, exactly as the contract computes it), and with zero borrows no interest accrues yet the borrow index still grows by the full factor. A per-block rate above the contract's maximum mantissa (0.0005e16 = 5000000000000 — "borrow rate is absurdly high") and a reserve factor above 1018 are refused, as is any product or total above the uint256 maximum. The prefilled market (rate 400000000000 per block, 10,000 blocks, 3,000,000 borrows, 100,000 reserves, a 10% reserve factor, borrow index 1018) accrues exactly 12,000 of interest: borrows become 3,012,000, reserves 101,200, and the index 1004000000000000000. Honest scope: rate, totals and index are values you supply — a real market's are chain state, which this page does not read, and its rate moves with utilization between accruals in a way a single supplied rate does not capture. This is CToken's formula applied to supplied values, not live market data and not financial advice. Computed locally; nothing is accrued and no chain is queried.

Compound account snapshot calculator (getAccountSnapshot)

The two Compound tools above work at market level; this one reads a single account the way CToken's getAccountSnapshot does — the stored snapshot the Comptroller itself uses for liquidity checks. An account's borrow is not stored as a live balance: the market stores the principal it borrowed and the borrow index at that moment (its snapshot index), and the current debt is principal × market borrow index ÷ snapshot index, truncated — plain integer arithmetic in the current source, not one of ExponentialNoError's Exp helpers. A principal of zero short-circuits to a zero balance before the snapshot index is ever read, so a zero snapshot index is refused only when a borrow exists (the contract would divide by it). The supply side converts the account's cToken balance through the stored exchange rate — cTokens × rate ÷ 1018, truncated — the stored-rate version of balanceOfUnderlying. The prefilled account chains the two tools above: it borrowed 1,000,000 when the index was 1018, the accrual step moved the market index to 1004000000000000000, so it owes exactly 1,004,000; and the 45,871,559 cTokens the exchange-rate tool mints are worth 999,999 underlying at that tool's stored rate of 21800000000000000. Compound interest rate model calculator (JumpRateModelV2)

The accrual calculator above takes a per-block borrow rate as an input; this one computes that rate the way a Compound market's interest rate model does. JumpRateModelV2 starts from utilization — borrows × 1018 ÷ (cash + borrows − reserves), with a market that has no borrows short-circuiting to 0 before the denominator is ever read — and prices borrowing on a two-slope curve through a kink: at or below the kink the per-block borrow rate is utilization × multiplierPerBlock ÷ 1018 + baseRatePerBlock, and above it the rate first reaches that same line at the kink, then climbs at the steeper jump multiplier on the excess utilization — the two branches agree exactly at the kink, so the curve bends but never jumps. The supply rate is what remains for suppliers after the reserve factor's skim: utilization × (borrowRate × (1 − reserveFactor) ÷ 1018) ÷ 1018. Every division truncates, exactly as the contracts truncate, and utilization can exceed 1018 when reserves exceed cash. The inputs are the model's stored per-block parameters (its constructor divides governance's per-year values by blocks per year — that setup step is not this math). The prefilled market (9,100,000 cash, 3,000,000 borrows, 100,000 reserves) sits at exactly 25% utilization, below its 80% kink, and its borrow rate comes out at exactly 400000000000 per block — the rate the accrual calculator above is prefilled with — with a supply rate of 90000000000 at the accrual tool's 10% reserve factor. Reserves above cash + borrows, a zero denominator while borrows exist, a reserve factor above 1018, and any product above the uint256 maximum are refused, as the contracts revert there. Honest scope: totals and parameters are values you supply — a real market's are chain state, which this page does not read, and which model a market uses (and its parameters) is a governance choice this page does not look up. This is the model's formula applied to supplied values, not live market data and not financial advice. Computed locally; nothing is borrowed or supplied and no chain is queried.

Compound liquidation seize calculator (liquidateCalculateSeizeTokens)

When a Compound account falls into shortfall, a liquidator repays part of its borrow and seizes collateral cTokens in return; the Comptroller prices that seizure with liquidateCalculateSeizeTokens, built from its ExponentialNoError Exp helpers — each step truncating before the next reads it: numerator = liquidationIncentive × priceBorrowed ÷ 1018, denominator = priceCollateral × exchangeRate ÷ 1018, ratio = numerator × 1018 ÷ denominator, then seizeTokens = ratio × actualRepayAmount ÷ 1018. Because every step truncates, the count can differ from the one-line formula repay × incentive × priceBorrowed ÷ (priceCollateral × exchangeRate) whenever an intermediate product is not a multiple of 1018. The calculator also shows what the seized cTokens redeem for at the same stored rate (the exchange-rate calculator's conversion — not part of the Comptroller function itself). The prefilled liquidation — repaying 100,000 of a $1 borrow against $2 collateral at a 0.05 stored exchange rate, with the Comptroller's 1.08 incentive — seizes exactly 1,080,000 cTokens, worth exactly 54,000 collateral underlying. A zero oracle price for either market is refused, as the contract returns its price error there; so are a zero exchange rate and a collateral price × rate product that truncates the denominator to zero, and any product above the uint256 maximum, as the contract reverts there. Compound account liquidity calculator (getHypotheticalAccountLiquidity)

Whether a Compound account may borrow or redeem — and whether it is liquidatable at all, the check the seize calculator above does not perform — is decided by the Comptroller's getHypotheticalAccountLiquidity, which weighs collateral against borrows in the oracle's normalised price units with its ExponentialNoError Exp helpers. This calculator applies that math to one market: tokensToDenom = (collateralFactor × exchangeRate ÷ 1018) × oraclePrice ÷ 1018 — two multiplications, each truncating before the next reads it, so the factor can differ from the one-line product whenever an intermediate product is not a multiple of 1018 and the price is large enough to amplify the discarded remainder — then collateral = tokensToDenom × cTokenBalance ÷ 1018 against borrows + effects = oraclePrice × borrowBalance ÷ 1018 + tokensToDenom × hypotheticalRedeem ÷ 1018 + oraclePrice × hypotheticalBorrow ÷ 1018, each term truncating once. Collateral above the borrow side is liquidity; anything else (equality included) leaves the difference as shortfall — a shortfall above zero is what makes an account liquidatable and what blocks a redeem or borrow. The prefilled account — 50,000,000 cTokens at a 0.02 stored rate and a 0.75 collateral factor against a $1 oracle price, owing 500,000 — holds exactly 750,000 of collateral value against 500,000 of borrows, so its liquidity is exactly 250,000 with no shortfall; raise the borrow to 900,000 and the same account shows a 150,000 shortfall. A zero oracle price is refused, as the contract returns its price error there; so is any product or sum above the uint256 maximum, as the checked arithmetic reverts there. Honest scope: the contract sums these terms over every market an account has entered — this one-market form is exact for an account in a single market and otherwise gives that market's contribution plus the hypothetical effects on it. Balances, factor, rate and price are values you supply — a real account's are chain state, which this page does not read — and the stored exchange rate is used without accruing interest, exactly as the contract's own note states. Compound liquidation allowed & max repay calculator (liquidateBorrowAllowed)

Compound borrow allowed calculator (borrowAllowed)

The liquidity calculator above weighs an account's collateral against its borrows — the Comptroller's borrowAllowed is the gate that runs that weighing before a new borrow, in a fixed order (compound-protocol, BSD-3-Clause; formulas paraphrased). First, a zero oracle price for the borrowed market returns the price error and the check stops — the borrow cap and the liquidity check are never reached, so an overflow in either is not a refusal on that path. Next, the market borrow cap: a cap of 0 means unlimited (and the addition is never computed then either); otherwise the contract adds the proposed borrow to the market's total borrows with checked addition and requires the result to stay strictly below the cap, so a borrow that lands the total exactly on the cap is refused as cap-reached — again before the liquidity check runs. Only then comes the hypothetical liquidity check (the calculator above, on this market, with the proposed borrow applied): a shortfall above zero blocks the borrow as insufficient liquidity, while a shortfall of exactly zero — the borrow exhausting the account's liquidity exactly — is allowed. Compound redeem allowed calculator (redeemAllowed)

The borrow calculator above runs the Comptroller's gate before a borrow; this one runs its gate before a redeem — redeemAllowed, in its own branch order (compound-protocol, BSD-3-Clause; formulas paraphrased). Compound transfer allowed calculator (transferAllowed)

A cToken transfer does not burn anything, yet the Comptroller still gates it — and the gate it runs is the redeem gate above, on the source account: transferAllowed's only numeric consideration (compound-protocol, BSD-3-Clause; formulas paraphrased) is whether the source could redeem the same number of cTokens, so it runs the internal redeem check with the transfer amount as the redeem amount and returns its verdict unchanged. That has three consequences worth seeing. First, the destination account is never read by this gate — its balance, borrows and membership change nothing here (it appears only in the COMP reward updates afterwards) — which is why this calculator takes no destination input at all. Second, there is no self-transfer shortcut: transferring to yourself runs the same check. Third, the source's membership decides the branch, exactly as for a redeem: a source that has not entered the market bypasses the liquidity check entirely, so a zero oracle price or an overflowing liquidity product is not a refusal there and the transfer amount is never weighed by this gate; only for a member source does the hypothetical liquidity check run with the transfer applied as a redeem — a shortfall above zero blocks the transfer, while a shortfall of exactly zero (the transfer exhausting the source's liquidity exactly) is allowed. Compound exit market calculator (exitMarket)

The redeem and transfer gates above weigh a partial removal of collateral; leaving a market entirely is a different Comptroller function — exitMarket (compound-protocol, BSD-3-Clause; formulas paraphrased) — and it asks a prior question first. The contract reads the account's snapshot in the market (the snapshot calculator's cToken balance and borrow balance) and refuses the exit at once if the account owes anything in this market: that nonzero-borrow-balance step comes before every membership step, so it refuses a non-member who owes a balance too, and price and factor are never read on that path. Only an account owing nothing reaches the internal redeem check — the redeem gate's own check — run with the redeem amount set to the account's full cToken balance: a non-member bypasses the liquidity check entirely (the exit succeeds; there is no membership to remove), while a member runs the hypothetical liquidity check with that full-balance redeem applied. That member path has a consequence worth seeing: the check's borrow balance is the amount owed — already known to be zero — and its redeem term is computed from exactly the same inputs as its collateral term, so the two cancel identically and the check completes with liquidity 0 and shortfall 0; the only refusals it can still produce are its own errors, a zero oracle price and any product or sum above the uint256 maximum. The prefilled account chains the liquidity calculator with its borrow repaid: 50,000,000 cTokens at a 0.02 stored rate and a 0.75 collateral factor against a $1 price, owing 0 — a member exit is allowed, and the 0 / 0 the check reports is not the 250,000 of liquidity the account holds while staying in the market. ModExp precompile gas calculator (EIP-2565 / EIP-7883 / EIP-7823)

Every EVM chain runs the modular-exponentiation precompile at address 0x05 — the RSA / VDF / signature-verification primitive — and a call's gas is not a price anyone sets: it is a formula over the call's shape, priced twice in Ethereum's history. The input names three lengths (base, exponent, modulus, in bytes) and the cost follows the two schedules' published pseudocode (EIP-2565, in force from Berlin, and EIP-7883, the Fusaka repricing live on mainnet — both schedules are shown, because which one applies is the chain's fork state and L2s and other EVM chains adopt repricings on their own schedules). Both start from a multiplication complexity over words = ceil(max(base length, modulus length) ÷ 8) — squared under EIP-2565; under EIP-7883 a flat 16 while the maximum is at most 32 bytes and twice the square above that — and an iteration count from the exponent: a zero exponent of at most 32 bytes counts 0, a short exponent counts its bit length minus 1, and a longer one counts a per-byte term (8 per byte past 32 under EIP-2565, 16 under EIP-7883) plus the bit length minus 1 of the exponent's head — its first 32 bytes, which is all of it the count ever reads; with a non-zero head that sum is exactly the exponent's own bit length minus 1. The count is floored at 1, then EIP-2565 charges max(200, complexity × iteration ÷ 3) (floored) while EIP-7883 charges max(500, complexity × iteration) — the divisor removed and the minimum raised, so a typical call costs about three times the old price and a long-exponent call far more. The Fusaka schedule also carries a validity cap the old schedule never had (EIP-7823): each of the three lengths — base, exponent and modulus, per length, not on the total input — must be at most 1,024 bytes (8,192 bits), and exactly 1,024 is allowed. If any one length exceeds that, the precompile stops, returns an error and consumes all gas forwarded to it, so this calculator quotes no EIP-7883 price for such a call and says so instead; the EIP-2565 price is still shown, because that schedule had no cap. The prefilled call (64-byte base and modulus, exponent 0x10001) costs 341 gas under EIP-2565 and 2,048 under EIP-7883 — the modexp_nagydani_1_pow0x10001 row of the two EIPs' own test tables, at those operand sizes. Honest scope: this prices a call under each formula from values you supply — it does not compute the modular exponentiation itself, and nothing is read from any chain. Computed locally; no call is made and no chain is queried.

SSTORE gas & refund calculator (EIP-2200 / EIP-2929 / EIP-3529)

One SSTORE has no single price: under net gas metering (EIP-2200) its cost follows from three values of the slot — the original value when the transaction began, the current value before this write, and the new value being written — with the parameters current mainnet applies (EIP-2929 raised first-touch state access; EIP-3529 cut the refunds). Writing the value the slot already holds is a no-op at the 100-gas warm read cost. A first, clean write (current still equals original) costs 20,000 to set a zero slot and 2,900 to change a non-zero one — earning a 4,800 credit on the transaction's refund counter when it clears the slot to zero. A later, dirty write to an already-changed slot costs 100, and the refund counter absorbs the difference instead: it falls by 4,800 when a slot cleared earlier in the same transaction is written away from zero again, rises by 4,800 when this write clears it, and rises by 19,900 (zero original) or 2,800 (non-zero original) when the write restores the original value — which is why a set-then-restore pair nets out near the warm cost, and why a dirty refund change can be negative. On top of the branch cost, a slot touched for the first time in the transaction adds the 2,100 cold surcharge. The prefilled write clears a cold slot that still holds its original value 1: 5,000 gas (2,900 + 2,100) and a 4,800 refund-counter credit. Honest scope: this prices one write from values you supply — a real slot's original and current values are chain and transaction state this page does not read; the stipend guard (a write fails when the frame's remaining gas is at most 2,300) is a validity rule, not part of the price, and is not modelled; and the refund cap — at most a fifth of the transaction's gas used, applied when the transaction ends — is not applied to this one write's counter change. Computed locally; nothing is written and no chain is queried.

Memory expansion gas calculator

Storage has the branch table above; memory — the EVM's byte-addressable scratch space that every call frame starts empty — has a formula instead, and it is the one part of an operation's price that depends on everything the frame has already touched. Memory is priced in 32-byte words by the Yellow Paper's cost function (the rule go-ethereum's memoryGasCost implements, with its parameters of 3 gas per word and a quadratic divisor of 512): holding w words costs, in total, 3w + floor(w² ÷ 512). An operation that grows memory pays only the increase — the new total minus the total for the size already held — and an operation that stays inside the size already paid for pays no expansion charge at all, which is why a frame's expansions telescope: growing in steps costs exactly the one-shot growth to the same size. The quadratic term is the point: it is zero below 23 words, equals the linear term's scale at 512 words (16 KiB, total 2,048), and dominates beyond it, so memory stays cheap for scratch work and punishing to hoard. Byte sizes round up to whole words on both sides, and a new size above 137,438,953,440 bytes (0x1FFFFFFFE0) is refused, as the client's gas calculation overflows there. The prefilled growth — from empty to 1,024 bytes — is 32 words and exactly 98 gas. Honest scope: this is the expansion charge only, from sizes you supply — the operation that touches memory (an MSTORE, a copy, a hash, a call) charges its own static and per-word costs on top, which are not modelled here, and a real frame's current size is execution state this page does not read. Computed locally; nothing is executed and no chain is queried.

CALL gas calculator (EIP-2929 / EIP-150)

Memory expansion is one ingredient of the EVM's most-used opcode: a CALL. Its price is a stack of rules charged in order, before any forwarding is worked out. First the access cost (EIP-2929): 2,600 if the target address is cold — not yet accessed in this transaction — and 100 if it is already warm. Then, if the call carries value, 9,000 for the transfer, plus 25,000 more if the target account is empty (nonce 0, balance 0, no code — funding it creates the account). Then the memory expansion above, for the input and output regions together: the frame must reach the larger of the two region ends, and a region of size 0 touches nothing whatever its offset. Only then does forwarding follow EIP-150's all-but-one-64th rule: of what remains after those costs, at most R − floor(R ÷ 64) can be forwarded — the caller always keeps at least a 64th in reserve — and the callee receives the smaller of the requested gas and that cap, plus, when the call carries value, a 2,300 stipend that is added for the callee and is not deducted from the caller (the rule that made the old fixed-stipend transfer idiom work at all). If the frame's gas does not cover the call's own cost, the CALL runs out of gas and forwards nothing. The prefilled call — a cold call carrying 1 ETH to an existing account, 100,000 gas available, 1,000,000 requested — pays 11,600 of its own costs, is capped at forwarding 87,019, delivers 89,319 to the callee with the stipend, and keeps exactly its 1,381 reserve (floor(88,400 ÷ 64)). Gas the callee does not use returns to the caller afterwards; this prices the split at the moment of the call. Honest scope: only CALL is modelled — CALLCODE, DELEGATECALL and STATICCALL share the access and forwarding rules but differ on the value terms — a call the caller cannot fund fails for a non-gas reason that is not modelled, and warmth, target state, value and memory are values you supply, not execution state this page reads. Computed locally; no call is made and no chain is queried.

CREATE & CREATE2 gas calculator (EIP-3860 / EIP-170)

A call forwards gas; a creation spends it in stages, and each stage has its own rule. First an upfront cost is deducted before the initcode runs: 32,000 for the operation itself; a metering charge on the initcode of 2 gas per 32-byte word (EIP-3860, charged for both opcodes so that initcode is paid for like calldata), plus 6 more per word under CREATE2, which hashes the initcode to derive the new address; and memory expansion for the region of the creator's memory the initcode is read from — the frame must reach the region end, and a zero-size region touches nothing whatever its offset. Of what remains, the initcode itself receives all but one 64th under EIP-150's rule — the same split the CALL calculator above applies — and the creator keeps the 64th at the moment of creation; gas the initcode leaves unused returns afterwards. Only when the initcode finishes and returns the runtime code does the last charge land: a code deposit of 200 per deployed byte, paid from the gas then remaining — if that cannot cover it, the creation fails. Two size limits fail a creation outright rather than pricing it: initcode above 49,152 bytes is refused by EIP-3860 (the limit is twice the code maximum), and runtime code above 24,576 bytes can never be deposited (EIP-170). Note what is absent: unlike a CALL carrying value, a creation charges nothing for moving its endowment — the value terms simply do not appear in this opcode's price. The prefilled creation — a CREATE with 500,000 gas available, 1,000 bytes of initcode at offset 0 in fresh memory, returning 800 bytes of code — pays 32,162 upfront (32,000 + 64 of word charges over 32 words + 98 of memory expansion), forwards 460,529 to the initcode, keeps exactly 7,309 in reserve, and owes a 160,000 deposit on success: 192,162 of fixed charges before the initcode's own execution. Honest scope: this prices a creation by opcode inside a frame — a contract-creation transaction folds the initcode into its intrinsic gas instead — the initcode's own execution (the opcodes it runs) is not modelled, a creation that fails because the target address is already occupied is not modelled, and the sizes and memory state are values you supply, not execution state this page reads. Computed locally; nothing is deployed and no chain is queried.

Other CALL opcodes gas calculator (CALLCODE / DELEGATECALL / STATICCALL)

The CALL calculator above deliberately left out CALL's three siblings — they share its rules but differ on the value terms, and the differences are the point. SELFDESTRUCT gas calculator (EIP-2929 / EIP-3529 / EIP-6780)

SELFDESTRUCT (0xff) ends a contract and sends its whole balance to a beneficiary, and its price under the rules current mainnet applies is a 5,000 base plus up to two situational terms. First, an EIP-2929 access term for the beneficiary: +2,600 if the beneficiary is cold — not yet touched in this transaction — and +0 if it is warm. Note this is an addition to the 5,000, not the whole cost the way it is for the account-access opcodes above: there is no 100 warm price here, because the 5,000 is not a warm read cost (a cold access still warms the beneficiary for later touches). Computed locally; nothing is destroyed and no chain is queried.

SIGNEXTEND opcode calculator — sign extension

Shift opcode calculator — SHL / SHR / SAR (EIP-145)

The native bitwise shifts Constantinople added, because the EVM originally had none and the arithmetic workarounds cost about 35 gas each: SHL (0x1b), SHR (0x1c) and SAR (0x1d) each pop a shift and a value — in that order, shift first, swapped against most arithmetic opcodes — and push the value shifted by that many bits, at a flat 3 gas each, the verylow tier. The three differ in what fills the vacated end and in how the value is read. SHL shifts left and wraps mod 2256, so bits pushed past bit 255 are simply lost. SHR is the logical right shift: the value is read unsigned and zeros fill from the top. SAR is the arithmetic right shift: the value is read as a signed two's-complement integer and its sign bit fills from the top, which makes it a division by a power of two that rounds toward minus infinity — SAR of −255 by 1 pushes −128, where the truncating SDIV would give −127, so SAR is not just an EXP/SDIV pair. These are the opcodes Solidity's << and >> compile to — >> on a signed type is SAR — so the calculator computes the pushed word and its signed reading, not just the charge. The prefilled call is the sign-fill case: SAR by 4 of 0xffff…ff00, the word for −256, pushes 0xffff…fff0, read as −16. Modular arithmetic opcode calculator — ADDMOD / MULMOD

Two Frontier opcodes that do modular arithmetic the way cryptography needs it: ADDMOD (0x08) pops a, b and a modulus N and pushes (a + b) mod N, and MULMOD (0x09) pushes (a × b) mod N — each at a flat 8 gas, the Mid tier. The defining property is precision: the intermediate sum or product is computed at full precision and is not reduced mod 2256 before the modulus is taken — an ADDMOD sum can reach 2257 − 2 and a MULMOD product 2512 − 2257 + 1, widths no stack word could hold. That is the whole point of the pair, and the trap for reimplementations: a calculator that wraps the product to a word first turns the prefilled call below into 2256 mod 2256 = 0, where the opcode's true answer is 38 (because 2255 ≡ 19 mod (2255 − 19), so 2256 ≡ 38). The operands are read unsigned (there is no signed variant; SMOD is a separate opcode), a and b are interchangeable, and N is the third, deepest of the three popped words. These are the standard way to do arithmetic over a large prime field — curve math, RSA-style exponentiation support — without a wide intermediate overflowing. BYTE opcode calculator

A Frontier opcode for pulling one byte out of a word: BYTE (0x1a) pops an index i and then a word x — index first — and pushes the byte of x at position i, placed at the least significant position of the pushed word, so the result is always between 0 and 255, at a flat 3 gas, the verylow tier. The defining subtlety is which end the index counts from: position 0 is the most significant byte of x, so the byte extracted is (x >> (248 − 8×i)) & 0xff. An index of 32 or more pushes 0: out of range is a defined result, not an error, which is what lets extraction code skip a bounds check. This is the opcode compilers emit when code indexes into a bytes32 or pulls a byte out of packed data. The prefilled call is the end-convention case: BYTE at index 0 of 0xab00…0001 pushes 171 (0xab), where a least-significant-first reading would push 1 — and at index 31 the true answer is 1. Division & modulo opcode calculator — DIV / SDIV / MOD / SMOD

The EVM's four division opcodes, all Frontier, all a flat 5 gas (the low tier): DIV (0x04) and MOD (0x06) read their operands unsigned; SDIV (0x05) and SMOD (0x07) read them as two's-complement signed. Each pops the dividend a first, then the divisor b. Three rules separate the opcodes from the division most programmers know. First, a divisor of 0 pushes 0 for all four — division by zero is a defined result, not an error (Solidity's / and % check first and revert with Panic(0x12); that check is the language's, not the opcode's, and this calculator computes the opcode). Comparison opcode calculator — LT / GT / SLT / SGT / EQ / ISZERO

The EVM's comparison opcodes, all Frontier, all a flat 3 gas (the verylow tier): LT (0x10), GT (0x11), SLT (0x12), SGT (0x13), EQ (0x14) and ISZERO (0x15). The five binary opcodes each pop a first, then b, and push 1 when the comparison holds and 0 when it does not — a comparison pushes 1 or 0, never an operand — and the comparisons are strict, so equal operands push 0 for LT, GT, SLT and SGT alike. ISZERO is the family's unary member: it pops one word only and pushes 1 exactly when that word is 0. The trap is the reading. LT and GT read their operands unsigned, as plain magnitudes; SLT and SGT read the same words as signed two's-complement integers — so one pair of words can answer oppositely under the two pairs. The all-ones word is the largest unsigned value there is, but read signed it is −1: against 1 it makes LT push 0 and SLT push 1, GT push 1 and SGT push 0. An implementation that compares every word unsigned passes every small-number test and is wrong on exactly the words with the top bit set — which is also why Solidity needs both pairs: its unsigned types compile to LT/GT and its signed types to SLT/SGT. EQ alone is reading-independent: the words are equal or they are not. The prefilled call is the flip: SLT of the all-ones word (read signed as −1) against 1 pushes exactly 1, where LT on the same words pushes 0. Bitwise opcode calculator — AND / OR / XOR / NOT

The EVM's bitwise opcodes, all Frontier, all a flat 3 gas (the verylow tier): AND (0x16), OR (0x17), XOR (0x18) and NOT (0x19). The three binary opcodes pop a first, then b, and push the bit-by-bit combination of the two words — a result bit is 1 exactly when both input bits are 1 (AND), when at least one is 1 (OR), or when exactly one is 1 (XOR). They work on the raw 256 bits, so unlike the comparison family above there is no signed pair and the words' signed or unsigned reading is irrelevant; and the three are commutative, so a and b are interchangeable, unlike SUB, DIV or LT. NOT is the family's unary member: it pops one word only and pushes that word with every one of its 256 bits flipped — NOT 0 pushes the all-ones word and NOT of the all-ones word pushes 0. The trap is that NOT is not negation. There is no NEG opcode: arithmetic negation is 0 − x (a SUB), and the two's-complement identity is −x = NOT(x) + 1, so NOT 1 pushes 0xffff…fffe, which reads as −2 signed, not the all-ones word that reads as −1 — an implementation that computes NOT as 0 − x, or borrows a language whose ~ is infinite-precision (Python's ~0 is −1, not the all-ones word), is off by one on every input. Solidity's ~x compiles to exactly this NOT, and its -x to the SUB-plus-one pattern, which is why the two differ there too. Arithmetic opcode calculator — ADD / MUL / SUB

The EVM's plain arithmetic opcodes, all Frontier: ADD (0x01), MUL (0x02) and SUB (0x03). Each pops a first, then b, and pushes the result reduced modulo 2256 — ADD pushes (a + b) mod 2256, MUL pushes (a × b) mod 2256, and SUB pushes (a − b) mod 2256 with a as the minuend. The defining rule is the wrap: no result traps, saturates or signals, so the all-ones word plus 1 pushes 0, 0 − 1 pushes the all-ones word, 2255 × 2 pushes 0 and 2255 × 3 pushes 2255. The checked overflow and underflow reverts of Solidity ≥ 0.8 are a language check inserted around these opcodes, not the opcodes' own behaviour — in unchecked blocks and raw assembly the wrap is what executes. SUB is not commutative and its order matters — 3 − 5 pushes 2256 − 2, not 2 — while ADD and MUL are commutative. There is no signed pair in this family (unlike DIV or the comparisons): addition, multiplication and subtraction modulo 2256 give the same word under either reading, which is why one opcode each serves both Solidity int and uint arithmetic. Gas is not uniform inside the family: ADD and SUB are a flat 3 (the verylow tier) while MUL is a flat 5 (the low tier) — quoting 3 for MUL is wrong on every call. The prefilled call is the underflow wrap: SUB of 0 by 1 pushes exactly the all-ones word, 2256 − 1. Push opcode calculator — PUSH0 / PUSH1–PUSH32 (EIP-3855)

The EVM's push family: PUSH1–PUSH32 (0x60–0x7f, Frontier) each read the next 1–32 bytes of code after the opcode byte as a big-endian integer and push it — those bytes are the high-order bytes of the pushed word — and PUSH0 (0x5f), added by EIP-3855 in Shanghai, pushes 0 with no immediate at all. The trap is what happens at the end of the code: if fewer bytes remain than the opcode reads, the missing bytes are the low-order ones and read as zero — the byte string is padded on the right — so a truncated PUSH2 carrying only 0xff pushes 0xff00 (65280), not 255; an implementation that pads on the left, the natural short-integer reading, is wrong on exactly the truncated pushes a disassembler meets at code end. Gas splits inside the family: PUSH0 is a flat 2 (the base tier) while every PUSH1–PUSH32 is a flat 3 (the verylow tier) whatever its width or value — the 1-gas saving over PUSH1 0x00, plus a saved code byte, is PUSH0's whole reason to exist, and zero is the most-pushed constant in real bytecode. The prefilled call is the truncation case: PUSH2 with only 0xff remaining pushes exactly 65280. Stack opcode calculator \u2014 POP / DUP1\u2013DUP16 / SWAP1\u2013SWAP16

The EVM\u2019s stack-shuffling opcodes, all Frontier: POP (0x50) removes the top item; DUP1\u2013DUP16 (0x80\u20130x8f) each push a copy of one item already on the stack; SWAP1\u2013SWAP16 (0x90\u20130x9f) each exchange the top item with a deeper one. Both families count from the top: DUPn copies the n-th item counting the top as 1 (so DUP1 copies the top itself), and SWAPn swaps the top with the (n + 1)-th item (so SWAP1 swaps the top two, and needs its partner one deeper than its number suggests). Counting from the bottom instead \u2014 the deepest item as 1 \u2014 is the family\u2019s classic implementation bug: it passes on shallow stacks and duplicates or swaps exactly the wrong word whenever the stack runs deeper than the index. A too-short stack is the other sharp edge, and unlike DIV by zero or an out-of-range BYTE it has no defined result: DUPn on fewer than n items, SWAPn on fewer than n + 1, or POP on an empty stack is a stack underflow \u2014 an exceptional halt that consumes the frame\u2019s remaining gas and reverts its state, which the calculator reports as a halt rather than inventing a result stack. Gas holds a quieter trap: all three families charge a flat 2, the base tier \u2014 one below the verylow 3 the push family charges, so copying that 3 overprices every DUP and SWAP by half again. These are the opcodes compilers shuffle relentlessly \u2014 every local variable read in compiled code is a DUP, every expression reorder a SWAP \u2014 and the ones a hand-written assembly bug most often misaims. The prefilled call is the orientation case: DUP3 of the stack 10, 20, 30 (30 on top) pushes a second copy of 10, the deepest item \u2014 a bottom-counting implementation pushes 30. Honest scope: the stack is a list of words you supply, deepest first, not execution state this page reads; at most 64 items are accepted (a real stack caps at 1024, and the mirror-image overflow of a DUP at that cap is out of scope here), and any word wider than 256 bits is refused rather than wrapped. JUMPDEST analyser — valid jump destinations in bytecode

Every JUMP (0x56) and JUMPI (0x57) in EVM code may land only on a JUMPDEST (0x5b, Frontier) — and not every byte that reads 0x5b is one. This analyser walks the bytecode you supply from pc 0 exactly the way the protocol's own validity rule defines the destination set: the next instruction sits one byte on for every opcode except PUSH1–PUSH32 (0x60–0x7f), whose immediate bytes it steps over — those bytes are data, not code — while PUSH0 (0x5f) has no immediate and steps by one like everything else. A 0x5b counts only when the walk lands on it as an instruction. The trap is the naive scan: grepping the raw bytes for 0x5b also matches every 0x5b inside push data, and a jump onto one of those is an invalid jump destination — an exceptional halt that consumes the frame's gas — in code where the byte looks exactly like a JUMPDEST. The analyser lists those impostor offsets separately so the difference is visible, and can answer for one destination you name. Memory opcode calculator — MLOAD / MSTORE / MSTORE8

The EVM's memory opcodes, all Frontier: MLOAD (0x51) pushes the 32 big-endian bytes at an offset, MSTORE (0x52) writes a word as 32 big-endian bytes at an offset, and MSTORE8 (0x53) writes a single byte. Memory is a byte array that every call frame starts empty and zero-initialised: bytes past its current end read as zero, a write past the end extends it with zeros in the gap, and offsets need not be aligned — a word stored at offset 4 straddles the first two 32-byte slots, which is exactly how packed structures land. Uniswap V3 liquidity amounts calculator

Built a position with the converter above? A position is liquidity L between a lower and an upper tick at the pool's current tick: at or below the range it is entirely token0, inside it it holds token0 over the part of the range above the current price and token1 over the part below, and at or above the range it is entirely token1. Honest scope: the ticks and amounts are values you supply — a real position's ticks and liquidity and the pool's current tick are chain state, which this page does not read, so this is the libraries' formula applied to supplied values, not live pool data and not financial advice. Computed locally; nothing is deposited and no chain is queried.

Uniswap V3 swap step calculator

Priced the position above — this prices one step of a swap against liquidity like it, with the exact integer math of SwapMath's computeSwapStep over SqrtPriceMath, both in v3-core. A pool swap is a loop of these steps within one tick range: you give the current tick, the target tick (the next initialized tick, or a price limit — its price is the step's boundary, and it sets the direction: a target below the current price swaps token0 for token1, a target above swaps token1 for token0), the in-range liquidity, the fee tier in hundredths of a bip (100 = 0.01%, 500 = 0.05%, 3000 = 0.3%, 10000 = 1%), and the specified amount in the input token's base units (exact-input mode) or the output token's (exact-output mode). The step moves the price toward the target until the amount is used up or the boundary is reached; the amount that would continue into the next range is reported as the remainder. Input-side amounts round up and output-side amounts round down, exactly as the library passes its rounding flags, and when an exact-input step stops short of the target, the whole leftover input is the fee — the library's remainder rule. The prefilled step (tick 0 toward −1000, liquidity 1000000000, 10000 in at 0.3%) sends 9970 plus a fee of 30 and receives 9969. Honest scope: the values are ones you supply — a real pool's price, liquidity and fee tier are chain state, which this page does not read, and a full swap crosses initialized ticks with changing liquidity, which a single step does not model — so this is the libraries' formula applied to supplied values, not a live quote and not financial advice. Computed locally; nothing is swapped and no chain is queried.

ENS namehash calculator (EIP-137)

Every ENS name maps to a 32-byte node: start from 32 zero bytes and fold each label in right-to-left with Keccak-256 — node = keccak256(node ++ keccak256(label)). Registries and resolvers key records by this node on Ethereum and every EVM L2. EIP-712 domain separator calculator

Typed-data signatures (EIP-712 — permits, off-chain orders, gasless approvals) are bound to a domain separator: the Keccak-256 of the ABI-encoded EIP712Domain struct — its type hash, the hashed name and version, the chain ID, and the verifying contract, one 32-byte word each. It is the value contracts expose as DOMAIN_SEPARATOR, and it changes with the chain, which is what stops a signature made for one chain or contract replaying on another. Honest scope: this covers the canonical four-field domain only — domains that omit fields or add a salt hash a different type string, and this tool will not guess at them. Defaults below are the EIP-712 specification's own Ether Mail example, so you can reproduce its published separator. Computed locally; nothing is signed and no wallet is involved.

EIP-2612 permit digest calculator

The domain separator above binds one real signature scheme: ERC-20 permit (EIP-2612), the gasless approval. Instead of sending an approve transaction, the owner signs the EIP-712 digest keccak256(0x1901 ‖ DOMAIN_SEPARATOR ‖ hashStruct(Permit)) off-chain, and anyone can submit that signature to the token's permit(owner, spender, value, deadline, v, r, s), which sets the allowance when the signer recovers to the owner, the nonce equals the owner's current permit nonce, and the deadline has not passed. The struct is Permit(address owner,address spender,uint256 value,uint256 nonce,uint256 deadline) under the published type hash 0x6e71edae…, hashed with each field as one ABI word. Two traps. The value is a raw uint256 in the token's base units — 1 USDC is 1000000, not 1 — and 2^256 − 1 as the value is the conventional unlimited approval, just as 2^256 − 1 as the deadline is the conventional no-expiry permit; both are accepted here because both are what real permits carry. And the domain is the token's own: USDC signs under the name “USD Coin” and EIP-712 version “2”, DAI under “Dai Stablecoin” and “1” — a digest computed under another token's name or version belongs to a different separator and recovers to nobody the token accepts. The defaults are USDC on Ethereum mainnet with a 1 USDC approval. Honest scope: this computes the digest only — whether the nonce is the owner's current one and whether the deadline has passed are chain state this page does not read, and a token that never implemented EIP-2612 has no permit to accept the signature at all. Nothing is signed, no key is used or asked for, and no chain is queried.

EIP-712 typed-data digest calculator (Ether Mail)

The domain separator above is only half of an EIP-712 signature. This tool computes that whole chain for the specification's own example schema, Mail(Person from, Person to, string contents) with Person(string name, address wallet), so the defaults below reproduce the published Ether Mail digest from the EIP's example implementation. Honest scope: this is that one fixed schema, not a general typed-data encoder — arbitrary schemas are out of scope rather than guessed at. Contents are hashed exactly as typed (whitespace counts). Computed locally; nothing is signed and no wallet is involved.

EIP-1559 gas cost estimator

A wallet-convention model, not live data: expected cost uses base + priority fee; max cost uses maxFeePerGas = 2×base + priority. A simple transfer is 21,000 gas.

Next-block base fee calculator (EIP-1559)

The estimator above prices a transaction given a base fee; this calculator applies EIP-1559's own update rule to a parent block you describe and derives the next block's base fee. The parent's gas target is its gas limit ÷ 2. A parent exactly at target leaves the fee unchanged; above target the fee rises by parent fee × (used − target) ÷ target ÷ 8 — never less than 1 wei — so a completely full parent raises it by exactly one eighth (12.5%); below target it falls by the same quotient, with no floor. The defaults are an illustrative full parent block (30,000,000 of 30,000,000 gas at 12 gwei), which lifts the next fee to 13.5 gwei. Honest scope: this is the protocol's formula applied to values you supply — not live network data; read a real parent block's base fee, gas used and gas limit from your own node or an explorer to derive the actual next fee. L2s run the same EIP-1559 mechanism with their own parameters (Base, an OP Stack chain, adjusts its fee parameters), so treat non-L1 numbers as the L1 rule illustrated, not a quote for that chain. Computed locally — nothing is sent and no chain is queried.

Intrinsic gas calculator (minimum gas limit)

Before any EVM execution runs, a transaction must carry a gas limit at least its intrinsic cost — the gas-units figure the estimator above takes as given. This calculator derives it from the transaction's data and lists. The standard cost is 21,000 base, plus calldata at 4 gas per zero byte and 16 per non-zero byte (EIP-2028 pricing), plus an EIP-2930 access list at 2,400 per address and 1,900 per storage key. A contract-creation transaction adds 32,000 plus EIP-3860's initcode metering — 2 gas per 32-byte word of initcode, rounded up — and initcode over 49,152 bytes is invalid, so it is refused here. An EIP-7702 set-code transaction adds 25,000 per authorization (and must have a destination, so authorizations cannot combine with creation). Since Prague, EIP-7623 also sets a calldata floor: counting each zero byte as 1 token and each non-zero byte as 4, the gas limit must reach 21,000 + 10 per token — the minimum is whichever of the standard cost and that floor is larger, and the floor binds on data-heavy transactions like the prefilled baz(uint32,bool) call (standard 21,344, floor 21,860). Honest scope: this is a minimum gas limit, not a prediction of total gas used — execution costs more, and L2s add their own fees and may adjust these parameters. Computed locally from the values you give — not live network data.

Proxy & namespaced storage slot calculator (ERC-1967 / ERC-7201)

Upgradeable proxies keep their logic address in a standard ERC-1967 slot — bytes32(uint256(keccak256(label)) − 1) — and ERC-7201 namespaced storage roots a struct at keccak256(abi.encode(uint256(keccak256(id)) − 1)) & ~0xff. Both derivations run locally here. This computes the slot constants only: to read a contract you pass a slot to eth_getStorageAt in your own tooling — this page reads no chain state.

ABI calldata encoder

Every contract call is one byte string: the 4-byte selector plus the arguments encoded by the Solidity ABI specification — static values as 32-byte words in place, dynamic values (bytes, string, arrays) as a head offset pointing at length-prefixed tail data, recursively for nested arrays. This encoder covers uint<M>/int<M>, address, bool, bytes<M>/bytes, string and fixed/dynamic arrays of those, nested — the same encoding on Ethereum, Base, Unichain and Robinhood Chain. Tuple and fixed-point types are out of scope and rejected rather than guessed at. Arguments are a JSON array: integers as decimal or 0x strings (a big uint256 in quotes can never lose precision), true/false for bool, 0x hex or plain text for bytes. The defaults are the ABI specification's own baz example, so you can reproduce its published calldata byte-for-byte. Encoded locally — nothing is sent and no transaction is made.

ABI calldata decoder

The encoder above, run backwards — paste calldata you meet in a block explorer or a failing transaction, give the function signature you believe it is for, and read the arguments back. Decoding here is strict: the 4-byte selector must match the signature, and non-canonical encodings are rejected rather than silently tolerated — a uint32 word with bits set above bit 31, a bool other than 0 or 1, an address with non-zero leading bytes, non-zero padding, an offset pointing into the head or past the end, a string that is not valid UTF-8, truncated data, or trailing bytes after the last argument. Decoded values come out in exactly the JSON form the encoder accepts (integers as decimal strings, addresses and bytes as 0x hex), so a decode re-encodes byte-for-byte. Same type scope as the encoder; tuple and fixed-point signatures are rejected. The defaults are the ABI specification's baz calldata, decoding back to [69, true]. Decoded locally — nothing is sent and no chain is queried.

Merkle root & proof calculator (sorted-pair Keccak tree)

Allowlists and airdrops commit a whole list to one 32-byte root, then prove each entry with a handful of sibling hashes. This calculator builds that tree locally, one leaf per line: a leaf is the Keccak-256 of its bytes (a 0x line contributes those hex bytes; any other line contributes its UTF-8 bytes — so an address leaf is just its 0x line). Each parent is the Keccak-256 of its two children sorted ascending before hashing — the commutative pair hashing OpenZeppelin's MerkleProof uses on-chain, so order inside a pair never matters — and an odd node at the end of a level is promoted unchanged rather than hashed against itself. Pick a leaf number to get its proof (the sibling list, bottom-up), which the tool then folds back to the root as a self-check. Caution, from OpenZeppelin's own documentation: if a root like this will be verified on-chain, keep leaf inputs away from exactly 64 bytes — a 64-byte preimage has the same shape as a concatenated pair of nodes; real airdrops hash an ABI-encoded entry (often twice) as the leaf instead of raw text. Computed locally — nothing is sent and no chain is queried.

RLP encoder & decoder

Almost everything Ethereum stores or sends — transactions, receipts, trie nodes, the CREATE address payload below — is serialized with RLP (Recursive Length Prefix): byte strings and nested lists of them, each prefixed by its length, with a single byte below 0x80 encoding as itself and integers carried as minimal big-endian byte strings (so the integer 0 is the empty string). The tools on this page build on an RLP codec internally; this one exposes it directly, in both directions. To encode, write one value: a "quoted string" or a bare word (its UTF-8 bytes), a 0x hex value (those raw bytes), a decimal integer, or a [list, of, values] nested to any depth. The prefilled list is the worked example the specification itself uses, so its encoding can be checked against it. Decoding is strict, exactly as in the transaction decoder below: non-canonical forms (a 0x81-prefixed small byte, the long length form for a short payload, a length with a leading zero), truncated input, and trailing bytes are refused rather than tolerated, and a decoded value must re-encode to exactly the bytes given. Byte strings render as 0x hex, with their text alongside when every byte is printable ASCII. Encoded and decoded locally — nothing is sent and no chain is queried.

Raw transaction decoder (RLP — legacy, EIP-2930, EIP-1559, EIP-4844 & EIP-7702)

Paste a raw transaction — the hex an explorer shows as “raw transaction” or a wallet hands you before broadcast — and see every field it actually carries: type, chain ID, nonce, fees, gas limit, destination (or contract creation), value, data, access list, and the signature fields, plus the two hashes derived from it: the signing hash (what the signer signed) and the transaction hash (its on-chain ID). The prefilled example is the signed transaction published in EIP-155 itself, so its decoding — nonce 9, 20 gwei, 21,000 gas, 1 ETH to 0x3535…3535, v 37 meaning chain ID 1 — and its published signing hash can be checked against the EIP. EIP-7702 set code transactions (type 4, the Pectra-era transactions that let an EOA delegate to contract code) decode too, including their authorization list — each tuple shown with its delegate address, chain ID, nonce and signature fields. EIP-4844 blob transactions (type 3, the Cancun-era transactions rollups use to post data to Ethereum) decode too, including their max fee per blob gas and their blob versioned hashes — the 32-byte commitments to the blobs, each starting with the KZG version byte 0x01. Decoding is strict: non-canonical RLP (a 0x81-prefixed small byte, long form for a short payload, leading-zero lengths or integers), wrong field counts, bad v values, and trailing bytes are all rejected rather than tolerated, and type 4 adds the EIP's own validity rules — a destination is required (no contract creation), the authorization list may not be empty, and each authorization's nonce must be below 264. Type 3 adds its own: a destination is required (a blob transaction cannot create a contract), the versioned-hash list may not be empty, and every hash must be exactly 32 bytes starting with 0x01. Honest scope: the signature is decoded, not verified — no sender is recovered — only the execution-payload form of a blob transaction is decoded (the pooled network wrapper that carries the blobs, KZG commitments and proofs alongside the payload during gossip is a different shape and is refused), and no KZG proof is checked — the blobs themselves are not part of the payload. Works identically for Ethereum, Base, Unichain, and Robinhood Chain transactions — same RLP, same EVM. Decoded locally — nothing is sent and no chain is queried.

Signature recovery (ecrecover) calculator

Every Ethereum signature names its signer — given the 32-byte digest that was signed and the signature's v, r and s, the signer's address is recoverable with the same secp256k1 math the EVM's ecrecover precompile runs, no private key involved. That is how a contract checks who authorised an action, and how you check which account a signature in a bug report really came from. The prefilled example is again EIP-155's published transaction: its signing hash with v 37 (chain ID 1, parity 0) and its published r and s recover the account of the private key the EIP prints, 0x9d8A62f656a8d1615C1294fd71e9CFb3E4855A4F. Paste any digest and signature — from the transaction decoder above, a typed-data digest, or a signed message — in any v form: 0/1, 27/28, or an EIP-155 value of 35 or more. Strict on purpose: r and s must be in range and s must sit in the lower half of the curve order — the canonical EIP-2 form every client enforces — so the malleable high-s twin of a signature is refused rather than recovered. Recovers an address from a signature only: nothing is signed, no key is used or asked for, and no chain is queried.

Signed message verification (EIP-191 personal_sign)

When a wallet pops up “sign this message”, it does not sign the message itself: EIP-191's personal_sign signs the digest keccak256("\x19Ethereum Signed Message:\n" ‖ length ‖ message) — the prefix guarantees the payload can never double as a transaction, and the length is the length in bytes, so a multibyte character counts more than once. Paste a message and the 65-byte signature a wallet returned and this tool rebuilds that digest and recovers the signer — the check behind “prove you control this address”, done with no key and no chain query. The defaults are a worked example whose signer (0x7E5F…5Bdf, the widely published address of private key 1) you can check the recovery against. Strict in the same way as the recovery tool above: the signature must be exactly 65 bytes and s must be the canonical low-s form, or it is refused rather than half-verified. Verifies a signature only: nothing is signed, no key is used or asked for.

Transaction sender recovery

The decoder above reads a signed transaction's fields but stops there; this tool takes the one step further every client takes before executing it — it recomputes the signing hash from the unsigned payload and recovers the sender from the transaction's own v / r / s with the ecrecover math above. That is the check behind “which account really sent this”, done from the raw hex alone. Blob gas & blob base fee calculator (EIP-4844 / EIP-7691)

The blob transactions the decoder above reads are priced in a second gas market of their own. EIP-4844 gives every block an excess_blob_gas header field — a running total of blob gas consumed above the block target — and sets the base fee per blob gas to fake_exponential(1, excess_blob_gas, update_fraction), a Taylor-series approximation of eexcess / fraction with a 1-wei floor, so the fee rises about 12.5% for each consecutive full Cancun block and falls when blocks run below target. Give this calculator the parent block's excess and blob gas used and it applies the EIP's own update rule (calc_excess_blob_gas) and pricing formula, then totals the blob fee for a transaction carrying your blob count — each blob is 131,072 blob gas, and the blob fee is burned, separate from the execution gas fee. Two schedules are offered because the numbers changed once already: Cancun as EIP-4844 launched it (target 3 blobs, max 6, fraction 3,338,477) and Prague as EIP-7691 raised it (target 6 blobs, max 9, fraction 5,007,716 — fuller blocks now move the fee about 8.2%). The defaults are a full Prague parent block (9 blobs), which lifts the excess by exactly the 3 above-target blobs' worth of blob gas while the fee still sits at its floor. Honest scope: this is the protocol's pricing rule applied to values you supply, not live network data — read a real block's excess_blob_gas from your own node or an explorer to price the current fee. Computed locally — nothing is sent and no chain is queried.

Blob versioned hash calculator (EIP-4844)

A blob transaction never carries a blob itself — it names each blob by a 32-byte versioned hash, the value the decoder above checks for the 0x01 first byte and the BLOBHASH opcode returns. EIP-4844 defines it from the blob's 48-byte KZG commitment (the compressed BLS G1 point in the blob sidecar) in one step: 0x01 ‖ SHA-256(commitment)[1:] — the version byte replaces the first byte of the commitment's SHA-256. Note the hash here is SHA-256, not Ethereum's usual Keccak-256 — the one place in the transaction format where the other hash appears, kept forward-compatible with the sharding design it was borrowed from. The prefilled commitment is the BLS point at infinity (0xc0 followed by 47 zero bytes — the identity point EIP-4844's commitment check explicitly allows), whose versioned hash is 0x010657f3…. Honest scope: this derives the hash from a commitment only — it does not compute the commitment from blob data (that is KZG/BLS cryptography needing a trusted-setup library), it does not verify any KZG proof, and it cannot check that the 48 bytes are a valid curve point, only that there are 48 of them. Derived locally — nothing is sent and no chain is queried.

Ethereum in 30 seconds

Ethereum L1 is the settlement layer: a global computer where smart contracts run and every transaction is secured by the full network. It is powerful but capacity-limited, so most everyday activity moves to Layer 2 rollups — chains that execute transactions cheaply off L1 and post proofs/data back to Ethereum, inheriting its security. Since EIP-1559, every L1 transaction burns a base fee that floats with demand, plus an optional priority fee (tip) — the estimator below models exactly that.

Base is Coinbase's L2, built on the OP Stack / Superchain. Unichain is Uniswap's L2, built for DeFi and cross-chain liquidity. Robinhood Chain is Robinhood's permissionless L2 for onchain finance and tokenized real-world assets, built on Arbitrum technology with ETH as its gas token — live per its official documentation. Same EVM, same Solidity, same tooling (viem, ethers.js, Foundry) across all of them — which is why one builder hub can cover all four.

CREATE2 address calculator (EIP-1014)

CREATE2 deploys a contract to an address you can know in advance: the last 20 bytes of Keccak-256 of 0xff ++ deployer ++ salt ++ keccak256(init code). Same deployer, salt and init code → same address on Ethereum, Base, Unichain and Robinhood Chain — the basis for counterfactual wallets and cross-chain deployments. Defaults below are EIP-1014's own Example 0. This only computes the address locally; nothing is deployed.

Uniswap V2 pair & V3 pool address calculator

Uniswap's factories deploy every pair and pool with CREATE2, so the address is fixed before the pair exists — by the factory, the two tokens, and the pair/pool bytecode's init code hash. This calculator runs that derivation locally, exactly as Uniswap's developer docs (V2) and the v3-periphery PoolAddress library (V3) publish it: the tokens are sorted so the numerically smaller address is token0 (the factories refuse identical or zero-address tokens, and so does this tool), the V2 salt is Keccak-256 of the two token addresses packed (40 bytes), while the V3 salt is Keccak-256 of abi.encode(token0, token1, fee) (three 32-byte words). The defaults are the canonical Ethereum-mainnet deployment, and the prefilled V3 example reproduces the well-known USDC/WETH 0.3% pool. Switching protocol swaps the factory and init code hash defaults to that protocol's — unless you have typed your own, which is never overwritten: on Base, Unichain, or a fork, enter that deployment's factory (and its init code hash, if it was compiled differently). A V3 fee must be a tier the factory has enabled, which is chain state. Honest scope: this computes where a pair/pool would live — whether one actually exists there is the factory's getPair/getPool chain query, which this page does not make. Computed locally; nothing is deployed and no chain is queried.

Uniswap V2 swap quote calculator

Found the pair with the calculator above — this prices a swap against it, with the exact integer math of UniswapV2Library in v2-periphery. A V2 pair holds the constant product of its two reserves and charges 0.3% on the input, applied as a 997/1000 factor: for an exact input the output is the fee-adjusted input times the output reserve, divided by the input reserve scaled by 1000 plus the fee-adjusted input, rounded down; for an exact output the required input is the same relation solved the other way, rounded up by 1 so the pair's invariant check passes. The third mode, spot quote, is just the reserve ratio — no fee, no price movement, and not a trade quote. Enter reserves and amounts in each token's base units (the raw integers the contracts use); the pair stores reserves as uint112, so a reserve at or above 2112 is refused. Price impact is measured against the pre-trade reserve ratio, includes the fee, and is shown truncated to 4 decimal places (the amounts themselves are exact). Single pair only — a multi-hop route chains this per hop — and forks charging a fee other than 0.3% are out of scope. Honest scope: the reserves are values you supply — a real pair's reserves are chain state (its getReserves), which this page does not read, so this is the library's formula applied to supplied values, not live pool data and not financial advice. Computed locally; nothing is swapped and no chain is queried.

Uniswap V2 liquidity mint & burn calculator

Priced a swap above — this works out the liquidity side of the same pair, with the exact integer math of UniswapV2Pair in v2-core (and its Math library's Babylonian integer square root). Mint: into an existing pair, the LP units minted are the minimum of the two sides' pro-rata amounts, amount × totalSupply ÷ reserve floored per side — so the scarcer side relative to the pair's ratio governs and an unbalanced deposit earns no credit for its excess. Into an empty pair (the first deposit, reserves and total supply all 0), the units minted are sqrt(amount0 × amount1) − 1000: the first 1000 units (MINIMUM_LIQUIDITY) are locked at the zero address forever. Burn: LP units pay out pro-rata from the pair's token balances — not its reserves, since balances can exceed reserves by donations and accrued fees — liquidity × balance ÷ totalSupply floored per side. A mint or burn that would pay out 0 on a side is refused, as the pair reverts, and no reserve or balance (or reserve plus deposit) may exceed 2112 − 1, the pair's uint112 storage bound. Amounts are in base units. The prefilled mint (10,000 / 40,000 into reserves of 1,000,000 / 4,000,000 with supply 2,000,000) mints exactly 20,000 LP units; the prefilled burn (10,000 LP units against balances of 1,010,000 / 4,040,000 and the resulting supply of 2,020,000) pays out exactly 5,000 / 20,000. Honest scope: reserves, balances and total supply are values you supply — a real pair's are chain state, which this page does not read — and the pair's optional protocol-fee mint (when the factory's feeTo is set) is not modelled, so the total supply you supply is taken as the supply at the liquidity event itself. This is the pair contract's formula applied to supplied values, not live pool data and not financial advice. Computed locally; nothing is deposited, burned or queried on chain.

ERC-4626 vault conversion calculator

A tokenized vault (ERC-4626) prices its shares against the assets it holds with a single exchange rate, applied the way OpenZeppelin's ERC4626 applies it — with virtual shares and one virtual asset added to the totals, the construction that blunts the first-deposit inflation attack: converting assets to shares multiplies by (totalSupply + 10offset) ÷ (totalAssets + 1), and shares to assets by the inverse, where the offset is the vault's _decimalsOffset() (0 in OpenZeppelin's default). The four modes are the standard's four preview functions, and each rounds in the vault's favour, exactly as the standard specifies: previewDeposit (assets in, shares out) and previewRedeem (shares in, assets out) round down, while previewMint (shares wanted, assets needed) and previewWithdraw (assets wanted, shares burned) round up. Enter totals and amounts in base units. The prefilled vault (1,000,000 assets backing 1,000,000 shares, offset 0) converts a deposit of 10,000 assets to exactly 10,000 shares — try the same deposit against a supply of 1 share and a million assets to see a deposit round to 0 shares, then raise the offset to 3 and watch it mint 1. Honest scope: totals are values you supply — a real vault's totalAssets and totalSupply are chain state, which this page does not read — and a vault's own limits (maxDeposit, balances, allowances) are not modelled. This is the standard's formula applied to supplied values, not live vault data and not financial advice. Computed locally; nothing is deposited and no chain is queried.

Compound cToken exchange rate & mint/redeem calculator

A Compound money market prices its cTokens with one exchange rate, computed the way CToken computes it: while no cTokens exist the stored rate is the market's initial exchange rate mantissa, and afterwards it is (cash + totalBorrows − totalReserves) × 1018 ÷ totalSupply, truncated — so the rate only grows as borrows accrue interest faster than reserves skim their share. Conversions run through the same rate with ExponentialNoError's truncating Exp math: minting mints amount × 1018 ÷ rate cTokens, redeeming cTokens pays tokens × rate ÷ 1018 underlying, and redeeming a chosen underlying amount burns amount × 1018 ÷ rate cTokens. Note the contrast with the ERC-4626 tool above: Compound truncates every step and never rounds up, so the prefilled market (8,000,000 cash, 3,000,000 borrows, 100,000 reserves, 500,000,000 cTokens supplied; rate 21800000000000000) mints 45,871,559 cTokens for 1,000,000 underlying, and redeeming exactly those cTokens pays back 999,999 — one base unit stays in the market. Amounts are in base units of each token (cTokens have 8 decimals, the underlying usually 18, which is why an initial rate like cDAI's 2×1026 looks large: it is the per-token rate scaled by 1018 across that decimal gap). Honest scope: totals are values you supply — a real market's cash, borrows, reserves and supply are chain state, which this page does not read — interest accrual up to the current block (exchangeRateCurrent) is not performed, and Comptroller liquidity checks, cash-availability checks and borrow/repay are not modelled. This is CToken's formula applied to supplied values, not live market data and not financial advice. Computed locally; nothing is supplied or redeemed and no chain is queried.

Compound interest accrual calculator (accrueInterest)

The exchange-rate tool above reads a Compound market's stored totals; this one performs the step that moves them. CToken's accrueInterest takes the market's per-block borrow rate (a mantissa scaled by 1018, as its interest rate model returns it) and the blocks elapsed since the last accrual, and computes a simple interest factor — rate × blocks — then, truncating at every step through ExponentialNoError: interest accumulated is factor × totalBorrows ÷ 1018, total borrows grow by that interest, total reserves grow by reserveFactor × interest ÷ 1018, and the borrow index grows to factor × borrowIndex ÷ 1018 + borrowIndex. Two behaviours worth seeing: it is simple interest over the gap (the rate is held constant for one accrual call, exactly as the contract computes it), and with zero borrows no interest accrues yet the borrow index still grows by the full factor. A per-block rate above the contract's maximum mantissa (0.0005e16 = 5000000000000 — "borrow rate is absurdly high") and a reserve factor above 1018 are refused, as is any product or total above the uint256 maximum. The prefilled market (rate 400000000000 per block, 10,000 blocks, 3,000,000 borrows, 100,000 reserves, a 10% reserve factor, borrow index 1018) accrues exactly 12,000 of interest: borrows become 3,012,000, reserves 101,200, and the index 1004000000000000000. Honest scope: rate, totals and index are values you supply — a real market's are chain state, which this page does not read, and its rate moves with utilization between accruals in a way a single supplied rate does not capture. This is CToken's formula applied to supplied values, not live market data and not financial advice. Computed locally; nothing is accrued and no chain is queried.

Compound account snapshot calculator (getAccountSnapshot)

The two Compound tools above work at market level; this one reads a single account the way CToken's getAccountSnapshot does — the stored snapshot the Comptroller itself uses for liquidity checks. An account's borrow is not stored as a live balance: the market stores the principal it borrowed and the borrow index at that moment (its snapshot index), and the current debt is principal × market borrow index ÷ snapshot index, truncated — plain integer arithmetic in the current source, not one of ExponentialNoError's Exp helpers. A principal of zero short-circuits to a zero balance before the snapshot index is ever read, so a zero snapshot index is refused only when a borrow exists (the contract would divide by it). The supply side converts the account's cToken balance through the stored exchange rate — cTokens × rate ÷ 1018, truncated — the stored-rate version of balanceOfUnderlying. The prefilled account chains the two tools above: it borrowed 1,000,000 when the index was 1018, the accrual step moved the market index to 1004000000000000000, so it owes exactly 1,004,000; and the 45,871,559 cTokens the exchange-rate tool mints are worth 999,999 underlying at that tool's stored rate of 21800000000000000. Any product above the uint256 maximum is refused, as the contract reverts there. Honest scope: principal, indexes, balance and rate are values you supply — a real account's are chain state, which this page does not read — and no interest accrual is performed, so the market index and rate you give are the stored ones (or the ones after an accrual step you ran above). This is CToken's formula applied to supplied values, not live market data and not financial advice. Computed locally; nothing is borrowed or supplied and no chain is queried.

Compound interest rate model calculator (JumpRateModelV2)

The accrual calculator above takes a per-block borrow rate as an input; this one computes that rate the way a Compound market's interest rate model does. JumpRateModelV2 starts from utilization — borrows × 1018 ÷ (cash + borrows − reserves), with a market that has no borrows short-circuiting to 0 before the denominator is ever read — and prices borrowing on a two-slope curve through a kink: at or below the kink the per-block borrow rate is utilization × multiplierPerBlock ÷ 1018 + baseRatePerBlock, and above it the rate first reaches that same line at the kink, then climbs at the steeper jump multiplier on the excess utilization — the two branches agree exactly at the kink, so the curve bends but never jumps. The supply rate is what remains for suppliers after the reserve factor's skim: utilization × (borrowRate × (1 − reserveFactor) ÷ 1018) ÷ 1018. Every division truncates, exactly as the contracts truncate, and utilization can exceed 1018 when reserves exceed cash. The inputs are the model's stored per-block parameters (its constructor divides governance's per-year values by blocks per year — that setup step is not this math). The prefilled market (9,100,000 cash, 3,000,000 borrows, 100,000 reserves) sits at exactly 25% utilization, below its 80% kink, and its borrow rate comes out at exactly 400000000000 per block — the rate the accrual calculator above is prefilled with — with a supply rate of 90000000000 at the accrual tool's 10% reserve factor. Reserves above cash + borrows, a zero denominator while borrows exist, a reserve factor above 1018, and any product above the uint256 maximum are refused, as the contracts revert there. Honest scope: totals and parameters are values you supply — a real market's are chain state, which this page does not read, and which model a market uses (and its parameters) is a governance choice this page does not look up. This is the model's formula applied to supplied values, not live market data and not financial advice. Computed locally; nothing is borrowed or supplied and no chain is queried.

Uniswap V3 tick ⇄ sqrtPriceX96 converter

A Uniswap V3 pool does not store a price directly: it stores sqrtPriceX96 — the square root of the token1/token0 price in Q64.96 fixed point — and a tick, the same price placed on a 1.0001 grid: sqrtPriceX96 = sqrt(1.0001tick) × 296. This converter runs TickMath's exact integer math locally, in both directions: tick → sqrt ratio as the library's Q128.128 factor product, divided by 232 rounding up; and sqrt ratio → tick as the greatest tick whose ratio is at most the input, exactly as getTickAtSqrtRatio brackets and resolves it. Ticks run from −887272 to 887272 (the ticks of prices 2−128 and 2128); in the reverse direction the maximum tick's own ratio is refused, as the library requires, because a pool price can never reach it. The raw price shown, (sqrtPriceX96 / 296)2, is truncated to 12 significant digits for display (the tick and sqrt ratio are exact) and ignores token decimals — a pool's human price additionally scales by 10(decimals of token0 − decimals of token1). The prefilled tick 1000 reproduces sqrtPriceX96 83290069058676223003182343270 and raw price 1.10516539260. Honest scope: the value is one you supply — a real pool's tick and sqrtPriceX96 are its slot0 chain state, which this page does not read, so this is TickMath applied to supplied values, not live pool data and not financial advice. Computed locally; nothing is swapped and no chain is queried.

Uniswap V3 liquidity amounts calculator

Built a position with the converter above? This calculator works out what a concentrated-liquidity position actually holds, with the exact integer math of LiquidityAmounts in v3-periphery over SqrtPriceMath in v3-core (both divisions floor). A position is liquidity L between a lower and an upper tick at the pool's current tick: at or below the range it is entirely token0, inside it it holds token0 over the part of the range above the current price and token1 over the part below, and at or above the range it is entirely token1. Amounts mode takes L and returns the two token amounts (rounded down, as the library computes position amounts); liquidity mode takes desired token amounts and returns the L they mint — the single-sided formula outside the range, the minimum of the two sides inside it — plus the amounts that L actually uses. The ticks are converted with TickMath, so every price is one a real pool can hold; liquidity is a uint128 in the contracts, so an L at or above 2128 is refused, as is a desired-amount pair too small to mint L of 1. Amounts are in each token's base units. The prefilled range (−1000 to 1000 at current tick 0, L = 1000000) holds exactly 48768 base units of each token. Honest scope: the ticks and amounts are values you supply — a real position's ticks and liquidity and the pool's current tick are chain state, which this page does not read, so this is the libraries' formula applied to supplied values, not live pool data and not financial advice. Computed locally; nothing is deposited and no chain is queried.

Uniswap V3 swap step calculator

Priced the position above — this prices one step of a swap against liquidity like it, with the exact integer math of SwapMath's computeSwapStep over SqrtPriceMath, both in v3-core. A pool swap is a loop of these steps within one tick range: you give the current tick, the target tick (the next initialized tick, or a price limit — its price is the step's boundary, and it sets the direction: a target below the current price swaps token0 for token1, a target above swaps token1 for token0), the in-range liquidity, the fee tier in hundredths of a bip (100 = 0.01%, 500 = 0.05%, 3000 = 0.3%, 10000 = 1%), and the specified amount in the input token's base units (exact-input mode) or the output token's (exact-output mode). The step moves the price toward the target until the amount is used up or the boundary is reached; the amount that would continue into the next range is reported as the remainder. Input-side amounts round up and output-side amounts round down, exactly as the library passes its rounding flags, and when an exact-input step stops short of the target, the whole leftover input is the fee — the library's remainder rule. The prefilled step (tick 0 toward −1000, liquidity 1000000000, 10000 in at 0.3%) sends 9970 plus a fee of 30 and receives 9969. Honest scope: the values are ones you supply — a real pool's price, liquidity and fee tier are chain state, which this page does not read, and a full swap crosses initialized ticks with changing liquidity, which a single step does not model — so this is the libraries' formula applied to supplied values, not a live quote and not financial advice. Computed locally; nothing is swapped and no chain is queried.

CREATE address calculator

The classic deployment opcode derives a contract's address from the creator alone: the last 20 bytes of Keccak-256 of the RLP encoding of [sender, nonce]. Know an account's nonce and you know the address its next deployment lands at — the same on Ethereum, Base, Unichain and Robinhood Chain. (CREATE2 above is the salt-based alternative.) Defaults below are the long-published worked example for this formula, so you can reproduce its known nonce-0 address. This only computes the address locally; nothing is deployed.

ENS namehash calculator (EIP-137)

Every ENS name maps to a 32-byte node: start from 32 zero bytes and fold each label in right-to-left with Keccak-256 — node = keccak256(node ++ keccak256(label)). Registries and resolvers key records by this node on Ethereum and every EVM L2. Honest scope: names are lowercased and must be ASCII labels — internationalised names need full UTS-46 normalisation first, which this tool does not do, so it rejects them rather than hashing them wrong. This computes the identifier locally; it does not look up any name or resolver.

EIP-712 domain separator calculator

Typed-data signatures (EIP-712 — permits, off-chain orders, gasless approvals) are bound to a domain separator: the Keccak-256 of the ABI-encoded EIP712Domain struct — its type hash, the hashed name and version, the chain ID, and the verifying contract, one 32-byte word each. It is the value contracts expose as DOMAIN_SEPARATOR, and it changes with the chain, which is what stops a signature made for one chain or contract replaying on another. Honest scope: this covers the canonical four-field domain only — domains that omit fields or add a salt hash a different type string, and this tool will not guess at them. Defaults below are the EIP-712 specification's own Ether Mail example, so you can reproduce its published separator. Computed locally; nothing is signed and no wallet is involved.

EIP-712 typed-data digest calculator (Ether Mail)

The domain separator above is only half of an EIP-712 signature. The full digest a wallet signs is keccak256(0x1901 ‖ domainSeparator ‖ hashStruct(message)), where the message struct is hashed field-by-field — strings as their Keccak-256, nested structs recursively as their own hashStruct. This tool computes that whole chain for the specification's own example schema, Mail(Person from, Person to, string contents) with Person(string name, address wallet), so the defaults below reproduce the published Ether Mail digest from the EIP's example implementation. Honest scope: this is that one fixed schema, not a general typed-data encoder — arbitrary schemas are out of scope rather than guessed at. Contents are hashed exactly as typed (whitespace counts). Computed locally; nothing is signed and no wallet is involved.

EIP-1559 gas cost estimator

A wallet-convention model, not live data: expected cost uses base + priority fee; max cost uses maxFeePerGas = 2×base + priority. A simple transfer is 21,000 gas.

Next-block base fee calculator (EIP-1559)

The estimator above prices a transaction given a base fee; this calculator applies EIP-1559's own update rule to a parent block you describe and derives the next block's base fee. The parent's gas target is its gas limit ÷ 2. A parent exactly at target leaves the fee unchanged; above target the fee rises by parent fee × (used − target) ÷ target ÷ 8 — never less than 1 wei — so a completely full parent raises it by exactly one eighth (12.5%); below target it falls by the same quotient, with no floor. The defaults are an illustrative full parent block (30,000,000 of 30,000,000 gas at 12 gwei), which lifts the next fee to 13.5 gwei. Honest scope: this is the protocol's formula applied to values you supply — not live network data; read a real parent block's base fee, gas used and gas limit from your own node or an explorer to derive the actual next fee. L2s run the same EIP-1559 mechanism with their own parameters (Base, an OP Stack chain, adjusts its fee parameters), so treat non-L1 numbers as the L1 rule illustrated, not a quote for that chain. Computed locally — nothing is sent and no chain is queried.

Intrinsic gas calculator (minimum gas limit)

Before any EVM execution runs, a transaction must carry a gas limit at least its intrinsic cost — the gas-units figure the estimator above takes as given. This calculator derives it from the transaction's data and lists. The standard cost is 21,000 base, plus calldata at 4 gas per zero byte and 16 per non-zero byte (EIP-2028 pricing), plus an EIP-2930 access list at 2,400 per address and 1,900 per storage key. A contract-creation transaction adds 32,000 plus EIP-3860's initcode metering — 2 gas per 32-byte word of initcode, rounded up — and initcode over 49,152 bytes is invalid, so it is refused here. An EIP-7702 set-code transaction adds 25,000 per authorization (and must have a destination, so authorizations cannot combine with creation). Since Prague, EIP-7623 also sets a calldata floor: counting each zero byte as 1 token and each non-zero byte as 4, the gas limit must reach 21,000 + 10 per token — the minimum is whichever of the standard cost and that floor is larger, and the floor binds on data-heavy transactions like the prefilled baz(uint32,bool) call (standard 21,344, floor 21,860). Honest scope: this is a minimum gas limit, not a prediction of total gas used — execution costs more, and L2s add their own fees and may adjust these parameters. Computed locally from the values you give — not live network data.

Proxy & namespaced storage slot calculator (ERC-1967 / ERC-7201)

Upgradeable proxies keep their logic address in a standard ERC-1967 slot — bytes32(uint256(keccak256(label)) − 1) — and ERC-7201 namespaced storage roots a struct at keccak256(abi.encode(uint256(keccak256(id)) − 1)) & ~0xff. Both derivations run locally here. This computes the slot constants only: to read a contract you pass a slot to eth_getStorageAt in your own tooling — this page reads no chain state.

ABI calldata encoder

Every contract call is one byte string: the 4-byte selector plus the arguments encoded by the Solidity ABI specification — static values as 32-byte words in place, dynamic values (bytes, string, arrays) as a head offset pointing at length-prefixed tail data, recursively for nested arrays. This encoder covers uint<M>/int<M>, address, bool, bytes<M>/bytes, string and fixed/dynamic arrays of those, nested — the same encoding on Ethereum, Base, Unichain and Robinhood Chain. Tuple and fixed-point types are out of scope and rejected rather than guessed at. Arguments are a JSON array: integers as decimal or 0x strings (a big uint256 in quotes can never lose precision), true/false for bool, 0x hex or plain text for bytes. The defaults are the ABI specification's own baz example, so you can reproduce its published calldata byte-for-byte. Encoded locally — nothing is sent and no transaction is made.

ABI calldata decoder

The encoder above, run backwards — paste calldata you meet in a block explorer or a failing transaction, give the function signature you believe it is for, and read the arguments back. Decoding here is strict: the 4-byte selector must match the signature, and non-canonical encodings are rejected rather than silently tolerated — a uint32 word with bits set above bit 31, a bool other than 0 or 1, an address with non-zero leading bytes, non-zero padding, an offset pointing into the head or past the end, a string that is not valid UTF-8, truncated data, or trailing bytes after the last argument. Decoded values come out in exactly the JSON form the encoder accepts (integers as decimal strings, addresses and bytes as 0x hex), so a decode re-encodes byte-for-byte. Same type scope as the encoder; tuple and fixed-point signatures are rejected. The defaults are the ABI specification's baz calldata, decoding back to [69, true]. Decoded locally — nothing is sent and no chain is queried.

Merkle root & proof calculator (sorted-pair Keccak tree)

Allowlists and airdrops commit a whole list to one 32-byte root, then prove each entry with a handful of sibling hashes. This calculator builds that tree locally, one leaf per line: a leaf is the Keccak-256 of its bytes (a 0x line contributes those hex bytes; any other line contributes its UTF-8 bytes — so an address leaf is just its 0x line). Each parent is the Keccak-256 of its two children sorted ascending before hashing — the commutative pair hashing OpenZeppelin's MerkleProof uses on-chain, so order inside a pair never matters — and an odd node at the end of a level is promoted unchanged rather than hashed against itself. Pick a leaf number to get its proof (the sibling list, bottom-up), which the tool then folds back to the root as a self-check. Caution, from OpenZeppelin's own documentation: if a root like this will be verified on-chain, keep leaf inputs away from exactly 64 bytes — a 64-byte preimage has the same shape as a concatenated pair of nodes; real airdrops hash an ABI-encoded entry (often twice) as the leaf instead of raw text. Computed locally — nothing is sent and no chain is queried.

RLP encoder & decoder

Almost everything Ethereum stores or sends — transactions, receipts, trie nodes, the CREATE address payload below — is serialized with RLP (Recursive Length Prefix): byte strings and nested lists of them, each prefixed by its length, with a single byte below 0x80 encoding as itself and integers carried as minimal big-endian byte strings (so the integer 0 is the empty string). The tools on this page build on an RLP codec internally; this one exposes it directly, in both directions. To encode, write one value: a "quoted string" or a bare word (its UTF-8 bytes), a 0x hex value (those raw bytes), a decimal integer, or a [list, of, values] nested to any depth. The prefilled list is the worked example the specification itself uses, so its encoding can be checked against it. Decoding is strict, exactly as in the transaction decoder below: non-canonical forms (a 0x81-prefixed small byte, the long length form for a short payload, a length with a leading zero), truncated input, and trailing bytes are refused rather than tolerated, and a decoded value must re-encode to exactly the bytes given. Byte strings render as 0x hex, with their text alongside when every byte is printable ASCII. Encoded and decoded locally — nothing is sent and no chain is queried.

Raw transaction decoder (RLP — legacy, EIP-2930, EIP-1559, EIP-4844 & EIP-7702)

Paste a raw transaction — the hex an explorer shows as “raw transaction” or a wallet hands you before broadcast — and see every field it actually carries: type, chain ID, nonce, fees, gas limit, destination (or contract creation), value, data, access list, and the signature fields, plus the two hashes derived from it: the signing hash (what the signer signed) and the transaction hash (its on-chain ID). The prefilled example is the signed transaction published in EIP-155 itself, so its decoding — nonce 9, 20 gwei, 21,000 gas, 1 ETH to 0x3535…3535, v 37 meaning chain ID 1 — and its published signing hash can be checked against the EIP. EIP-7702 set code transactions (type 4, the Pectra-era transactions that let an EOA delegate to contract code) decode too, including their authorization list — each tuple shown with its delegate address, chain ID, nonce and signature fields. EIP-4844 blob transactions (type 3, the Cancun-era transactions rollups use to post data to Ethereum) decode too, including their max fee per blob gas and their blob versioned hashes — the 32-byte commitments to the blobs, each starting with the KZG version byte 0x01. Decoding is strict: non-canonical RLP (a 0x81-prefixed small byte, long form for a short payload, leading-zero lengths or integers), wrong field counts, bad v values, and trailing bytes are all rejected rather than tolerated, and type 4 adds the EIP's own validity rules — a destination is required (no contract creation), the authorization list may not be empty, and each authorization's nonce must be below 264. Type 3 adds its own: a destination is required (a blob transaction cannot create a contract), the versioned-hash list may not be empty, and every hash must be exactly 32 bytes starting with 0x01. Honest scope: the signature is decoded, not verified — no sender is recovered — only the execution-payload form of a blob transaction is decoded (the pooled network wrapper that carries the blobs, KZG commitments and proofs alongside the payload during gossip is a different shape and is refused), and no KZG proof is checked — the blobs themselves are not part of the payload. Works identically for Ethereum, Base, Unichain, and Robinhood Chain transactions — same RLP, same EVM. Decoded locally — nothing is sent and no chain is queried.

Signature recovery (ecrecover) calculator

Every Ethereum signature names its signer — given the 32-byte digest that was signed and the signature's v, r and s, the signer's address is recoverable with the same secp256k1 math the EVM's ecrecover precompile runs, no private key involved. That is how a contract checks who authorised an action, and how you check which account a signature in a bug report really came from. The prefilled example is again EIP-155's published transaction: its signing hash with v 37 (chain ID 1, parity 0) and its published r and s recover the account of the private key the EIP prints, 0x9d8A62f656a8d1615C1294fd71e9CFb3E4855A4F. Paste any digest and signature — from the transaction decoder above, a typed-data digest, or a signed message — in any v form: 0/1, 27/28, or an EIP-155 value of 35 or more. Strict on purpose: r and s must be in range and s must sit in the lower half of the curve order — the canonical EIP-2 form every client enforces — so the malleable high-s twin of a signature is refused rather than recovered. Recovers an address from a signature only: nothing is signed, no key is used or asked for, and no chain is queried.

Signed message verification (EIP-191 personal_sign)

When a wallet pops up “sign this message”, it does not sign the message itself: EIP-191's personal_sign signs the digest keccak256("\x19Ethereum Signed Message:\n" ‖ length ‖ message) — the prefix guarantees the payload can never double as a transaction, and the length is the length in bytes, so a multibyte character counts more than once. Paste a message and the 65-byte signature a wallet returned and this tool rebuilds that digest and recovers the signer — the check behind “prove you control this address”, done with no key and no chain query. The defaults are a worked example whose signer (0x7E5F…5Bdf, the widely published address of private key 1) you can check the recovery against. Strict in the same way as the recovery tool above: the signature must be exactly 65 bytes and s must be the canonical low-s form, or it is refused rather than half-verified. Verifies a signature only: nothing is signed, no key is used or asked for.

Transaction sender recovery

The decoder above reads a signed transaction's fields but stops there; this tool takes the one step further every client takes before executing it — it recomputes the signing hash from the unsigned payload and recovers the sender from the transaction's own v / r / s with the ecrecover math above. That is the check behind “which account really sent this”, done from the raw hex alone. The prefilled example is again EIP-155's published transaction, recovering 0x9d8A62f656a8d1615C1294fd71e9CFb3E4855A4F — the account of the private key the EIP prints. Strict in the same way as the tools it composes: the transaction must strictly decode and be signed (an unsigned transaction has no sender), and s must be the canonical low-s form, so a malleable high-s twin is refused rather than recovered. For an EIP-7702 set code transaction it also recovers each authorization's authority — the account that signed that delegation — from the tuple's own digest, keccak256(0x05 ‖ rlp([chain_id, address, nonce])); an authorization whose signature does not recover is reported as unrecoverable instead of guessed, exactly as a client skips that tuple and processes the rest. Recovers addresses only: nothing is signed, no key is used or asked for, and no chain is queried.

EIP-712 typed-data signature verification (Ether Mail)

The digest calculator above computes the hash a wallet signs for EIP-712 typed data; this tool completes the check a dapp or contract performs on the signature that comes back: it recomputes the digest keccak256(0x1901 ‖ domainSeparator ‖ hashStruct(message)) for the same domain and Mail fields and recovers the signer from the 65-byte eth_signTypedData signature with the ecrecover math above — “did this account really sign this exact typed data, for this exact domain?”, answered with no key and no chain query. The defaults are the specification's own worked example end to end: the signature below is the one EIP-712 itself prints as the result of its example request, and it verifies to its published signing account, Cow (0xCD2a…D826), over the published Ether Mail digest — change any field and the recovered signer changes with it, because the domain and every field are inside the hash. Honest scope is the digest tool's: this is that one fixed Ether Mail schema, not a general typed-data verifier — arbitrary schemas are out of scope rather than guessed at. Strict in the same way as the verifiers above: the signature must be exactly 65 bytes and s must be the canonical low-s form, or it is refused rather than half-verified. Verifies a signature only: nothing is signed, no key is used or asked for.

Blob gas & blob base fee calculator (EIP-4844 / EIP-7691)

The blob transactions the decoder above reads are priced in a second gas market of their own. EIP-4844 gives every block an excess_blob_gas header field — a running total of blob gas consumed above the block target — and sets the base fee per blob gas to fake_exponential(1, excess_blob_gas, update_fraction), a Taylor-series approximation of eexcess / fraction with a 1-wei floor, so the fee rises about 12.5% for each consecutive full Cancun block and falls when blocks run below target. Give this calculator the parent block's excess and blob gas used and it applies the EIP's own update rule (calc_excess_blob_gas) and pricing formula, then totals the blob fee for a transaction carrying your blob count — each blob is 131,072 blob gas, and the blob fee is burned, separate from the execution gas fee. Two schedules are offered because the numbers changed once already: Cancun as EIP-4844 launched it (target 3 blobs, max 6, fraction 3,338,477) and Prague as EIP-7691 raised it (target 6 blobs, max 9, fraction 5,007,716 — fuller blocks now move the fee about 8.2%). The defaults are a full Prague parent block (9 blobs), which lifts the excess by exactly the 3 above-target blobs' worth of blob gas while the fee still sits at its floor. Honest scope: this is the protocol's pricing rule applied to values you supply, not live network data — read a real block's excess_blob_gas from your own node or an explorer to price the current fee. Computed locally — nothing is sent and no chain is queried.

Blob versioned hash calculator (EIP-4844)

A blob transaction never carries a blob itself — it names each blob by a 32-byte versioned hash, the value the decoder above checks for the 0x01 first byte and the BLOBHASH opcode returns. EIP-4844 defines it from the blob's 48-byte KZG commitment (the compressed BLS G1 point in the blob sidecar) in one step: 0x01 ‖ SHA-256(commitment)[1:] — the version byte replaces the first byte of the commitment's SHA-256. Note the hash here is SHA-256, not Ethereum's usual Keccak-256 — the one place in the transaction format where the other hash appears, kept forward-compatible with the sharding design it was borrowed from. The prefilled commitment is the BLS point at infinity (0xc0 followed by 47 zero bytes — the identity point EIP-4844's commitment check explicitly allows), whose versioned hash is 0x010657f3…. Honest scope: this derives the hash from a commitment only — it does not compute the commitment from blob data (that is KZG/BLS cryptography needing a trusted-setup library), it does not verify any KZG proof, and it cannot check that the 48 bytes are a valid curve point, only that there are 48 of them. Derived locally — nothing is sent and no chain is queried.
